# Checks

The checks that hold the repository's own claims true. Each has a named command in the [Makefile](../Makefile) that runs it from the repository root and returns a nonzero status when it fails, so a developer and a continuous-integration job invoke the same name.

| Check | Command | Asserts | Fails on |
| --- | --- | --- | --- |
| `layout.py` | `make layout` | The repository holds a tree for the fixture corpus, one for the build and one for documentation. | A tree that holds no tracked file. |
| `links.py` | `make links` | Every reference every document the repository owns carries resolves, the fixture corpus excepted. | A path that does not exist, a fragment no heading generates, a git ref or path absent from the engineering branch, or a remote address whose host answered about the target, that it is not there, that the method a reader uses is not allowed, or that credentials are required. |
| `tables.py` | `make tables` | The README tables that enumerate the repository's commands and the project's dependencies name exactly what the `Makefile` and `src/pyproject.toml` declare. | A target or a dependency no table names, a table row naming a target or a dependency the project does not declare, or a row naming a version the project does not pin. |
| `vocabulary.py` | `make vocabulary` | The shipped glossary and the contract carry one vocabulary between them. | A term the design marks as a contract term and `docs/glossary.md` does not define, a marked term the glossary names as deliberately not used, or a definition neither the design marks nor an acceptance criterion uses. |
| `manifests.py` | `make harness` | Every fixture the corpus holds is a fixture the manifest schema describes. | A manifest leaving out one of the five declarations, carrying a field the schema does not describe, naming a code outside the catalogue its diagnostic's severity selects, naming a path the fixture does not hold, declaring absent a path the fixture holds, or naming an allowed source root the fixture holds while declaring that the run cannot find it. |
| `runner.py` | `make harness` | A fixture's run against the build under test produces the result its manifest declares. | A differing exit status, standard output differing in any byte, a diagnostic missing, extra, out of order, or carrying another value in a field the manifest declares, or a path the manifest declares absent that the run created. |
| `corpus.py` | `make corpus` | Every fixture the corpus holds produces, against the build under test, the result its manifest declares. | A fixture whose run differs from its manifest, a fixture awaiting later work that meets its manifest instead, or no build configured. |
| `conformance.py` | `make conformance` | Each behavioural clause of the design carries the fixtures exercising it, each name the contract declares is reached by a fixture or named unfixturable, and each installation claim no run of the corpus observes is listed as unfixturable with the reason it is unreachable and what would make it observable. | A manifest declaration naming no clause the design states, or an error code, warning code or exit status no fixture declares. |
| `independence.py` | `make independence` | The corpus and its conformance report bind the behaviour the design states rather than an implementation of it. | A fixture declaration, a report entry or a name the contract declares as its interface that names an implementation language or runtime, the machinery of modules and packaging, a source file of an implementation, an identifier a language reserves, a fault class of an implementation, or the wording a build gives its own fault. |
| `invocation.py` | `make invocation` | The invocation this repository documents is the invocation the build under test offers. | An argument or an exit status the command reports and no table names, a table row naming one the command does not report, a row whose text differs from the command's own help, a profile identifier the documented invocation does not name, or a statement the contract requires of it that the section does not carry. |
| `smoke.py` | `make smoke` | The build installs into an environment and its entry point bundles a reference from a source root, resolved by name outside this repository. | A wheel that does not build or install, an installed environment naming no command, a command resolving inside the repository, a version response naming no profile, a bundle differing from the one the source names, or a run writing to standard error or exiting nonzero. |

`make check` runs these eleven alongside the Python build's tests and static checks, in one pass over the repository.

`smoke.py`, `layout.py`, `links.py`, `tables.py` and `vocabulary.py` are standalone Python 3 scripts with no dependency beyond the standard library, run under `python3` directly. `manifests.py` and `runner.py` are the corpus's own modules rather than commands of their own, and `make harness` runs the suite in [`tests/`](tests), which exercises both of them and the reading every other check does. `corpus.py`, `invocation.py`, `conformance.py` and `independence.py` are commands, run from the locked environment because they read `runner.py` or the manifest reader beneath it. `documents.py` is a module too: it holds the documents the checks read and the reading they share, so one discovery serves both, `links.py` reading every document and `tables.py` the READMEs among them, which is where the project's command and dependency tables sit.

`manifests.py` is the manifest reader and validator: it reads [`fixtures/manifest.schema.json`](../fixtures/manifest.schema.json) through `jsonschema` from the locked development group and applies it to every fixture. `runner.py` reads its validation from that same module, so a manifest is checked the same way wherever it is read. A manifest's declared diagnostics decide which rule its allowed source root is held to: one declaring `E_ROOT_NOT_FOUND` has declared a run that cannot find that root, so the path is one the fixture must not hold, and every other manifest names a directory it must. The outcome is stated once, by the diagnostic, so the fixture carries no second declaration of it that could disagree.

`runner.py` runs one fixture. It reads the manifest, invokes the build under test against the fixture's source tree, and compares the run's standard output, exit status, diagnostics and the paths it leaves absent with what the manifest declares. The build is named by configuration — the environment variable `PROSIFORM_BUILD` holds its command line — and invoked as a subprocess, so the module imports no package, names no module and names no language. There is no default build: an unset variable raises rather than returning a verdict, so a fixture is never reported as holding against a build that never ran. The runner supplies the allowed source root and asks for diagnostics as data, which the contract's command line spells `--root DIR` and `--diagnostics json`, so a code is compared as a value rather than as prose. It asks for the fault a manifest names the same way, as `--fault NAME`: two of the contract's outcomes are facts about the run rather than about any document it reads, so a source tree and an invocation state neither, and the detection the fixture compares stays the build's own. A fault writes to the tree it runs over, so a fixture declaring one runs in a copy of itself and the fixture is left as it was.

A mismatch names the expectation that differed and locates the difference inside it. Standard output is compared as bytes and reported by byte offset, line and column, each window spelling its control bytes, so a CRLF against an LF reads as a difference rather than as two identical lines. Diagnostics are compared in order on the fields the manifest declares: one missing, one extra, a pair in the wrong order, and a field carrying another value are each reported as what they are, and a diagnostic carrying more than the manifest declares matches. A run's working directory is the fixture's own, so a path an invocation writes lands among the fixture's files: each path the manifest declares absent is checked once the run completes, and a file found there is reported with the bytes it carries and removed, so the directory a fixture leaves behind is the one its manifest declares. `PROSIFORM_BUILD_TIMEOUT` bounds a run in seconds, and a run that exceeds it fails the fixture.

`corpus.py` runs the whole corpus. It walks every fixture `manifests.py` discovers, in path order, puts each through `runner.py`, prints a line for each so the set it ran is visible, and returns a nonzero status when one of them fails. A failing fixture is named by its identity — its path under `fixtures/` — and its differences are printed under it, so a red run names which fixture rather than saying the corpus failed. A build it cannot reach fails the run: a corpus run that skips because nothing is configured sits inside a passing suite saying nothing.

The corpus declares the contract in full, so a manifest may name the work that delivers what it expects with `awaiting`. A fixture carrying that marker and failing is reported as awaiting that work and leaves the run green; one carrying it and meeting its manifest fails the run, so the marker is lifted on the change that makes it untrue rather than outliving the work it waits on. The marker sits in the manifest beside the expectation it qualifies, because a list of exceptions held anywhere else drifts from the fixtures it names in both directions.

Those markers also answer a question the other way round. `corpus.py --awaiting WORK` reports the fixtures declaring that work, each by its identity, with a count beneath them, so a session starting a piece of work reads what it unblocks before it changes anything. The request reads manifests alone, which is why it needs no build and returns zero whatever it finds: it is a report rather than a verdict. The name is compared as the manifest declares it, so a marker naming an epic and one naming a task within it answer separate requests, and a work item is asked about by the identity its fixtures were marked with.

`smoke.py` is the one check that does not run the build from this checkout. It builds the wheel, installs it into a throwaway environment outside the repository on the Python version `src/.python-version` names, looks the command up in that environment's executable directory alone, and invokes it by name from a temporary working directory against a source root written beside it. The invoked process inherits no variable of the run: its path holds that one directory, so an entry point the packaging never declared fails at the lookup and one that reads the repository fails at the bundle. Every other run of the build in these checks goes through `uv run --project src`, which names the checkout and so says nothing about whether an installation carries a command at all. The steps depend on each other in order, so the run stops at the first that fails and names it, and the environment is removed whatever the outcome.

`documents.py` finds a document the way `layout.py` finds a tree: git tracks it. Nothing lists the documents, so a document added later comes into the checks by being committed, and neither check is edited. The fixture corpus is excepted, and the exception is the corpus rather than a list of names: a fixture is a directory holding a manifest, which is what `manifests.py` calls one, and git lists those manifests alongside the documents, so a fixture added anywhere is excepted. A fixture's source deliberately carries references a run is meant to refuse and its expected bundle is output rather than a document a reader follows, so resolving either would fail by design. [`fixtures/README.md`](../fixtures/README.md) sits above every fixture rather than inside one, so it is read like any other document. `documents.py` also blanks literal content before a document is read and parses its pipe tables, so an example is never mistaken for a reference or a row. A fenced block goes before either reading; a reference scan blanks indented blocks and code spans beside it, so a link form written to show the syntax is passed over while a link beside it is resolved, which is the answer the product reaches about the same bytes. A heading's slug and a table's cell reduce a code span to its code instead, since that is what the rendering leaves behind.

`links.py` reads every document `documents.py` finds, and reaches addresses outside this repository only with `--online`, which the named command supplies: without the flag a remote reference counts as unresolved, so an offline run cannot pass. References into this repository's own branches resolve through git, so they need no network. An issue, a pull request or a project board is read through `gh api` with the caller's credentials, because a private repository answers an unauthenticated request with 404. Naming documents on the command line checks those instead, which is for reading one document while editing it.

A host that says nothing is told apart from a reference that does not resolve. A status of 400 or above below 500, 403 excepted, is the host answering about the target, and the document is held to it. A status of 500 or above, a status of 403, a connection that failed and a request that timed out each mean the host reported nothing about the target, so the address is attempted three times with a growing delay and then counted as unreachable: the run prints a `WARN` line naming it, states the count beside the references that resolved, and passes. The repository cannot fix a third party, and a check that fails on one teaches a reader to re-run it rather than to read it, which is the habit that lets a genuine broken reference through. An offline run is not this case: without `--online` a remote reference counts as unresolved, because the reader chose not to look.

403 sits among the statuses that say nothing because a refusal turns on the caller rather than on the target. Hosts a technical document routinely names — `www.nytimes.com`, `stackoverflow.com` and `medium.com` among them — answer 403 to both `HEAD` and `GET` for pages that are live and correct, and answer it to a browser's user agent as readily as to this check's, so the refusal follows the network the request came from. The same address serves the reader who follows it and refuses the run that checks it, which makes the status a fact about where the check ran rather than about the reference. Holding a document to it reddens a branch over a reference a reader can follow, and the verdict the branch carries is a third party's to change. Nothing is hidden by the choice: a refused address is named on its own `WARN` line every run, so a reference that is genuinely forbidden to everyone is reported rather than passed in silence, and a line that persists is followed once by hand to settle it. A host answering 403 or 405 to `HEAD` alone is answering about the method rather than about the target, so the address is asked again with `GET` and resolves on the page it serves. The warning is reserved for a host refusing both.

401 and 405 sit beside 403 and are held to, each for a reason of its own. A status of 405 names the methods the address allows, which is a fact about the target rather than about the caller: `httpbin.org/post` answers it to `HEAD`, to `GET` and to a browser's user agent alike, so the reader following the reference meets what the check met, and a document naming such an address names one no reader can read. A status of 401 names an authorization scheme the caller could satisfy, and a reference a reader must hold credentials to follow is one the document should say so about; `api.github.com/user`, `registry.npmjs.org/-/whoami` and `api.openai.com/v1/models` answer it to every caller holding none. One live home page, `www.reuters.com`, answers 401 to both methods and to a browser's user agent, which is the 403 shape wearing an authentication header, and it is the one case the failing verdict costs. It is outweighed by what counting 401 as silence would cost: `gh api` reports 401 when this check's own credentials are missing or stale, so a run that read no tracker reference at all would warn and pass. 401 is the one status that can name the check's own standing, and silence about that is silence about everything the check was asked to read.

The boundary is the same whichever way the read went out. A tracker reference is read by `gh api --include`, which writes the response's own status line, and that status is given to the one function the paragraphs above describe, so an issue, a pull request or a project board takes the verdict any other host answering that status takes. A call carrying no status line never received a response, which is the host saying nothing for a reason of its own. A failure whose status states nothing against the call is reported as the command gave it: a GraphQL error arrives under a 200, so a project board that is not there is an unresolved reference rather than a status to classify.

`tables.py` locates a table by its header rather than by the document or the section it sits in: a header cell `Command` makes a table an enumeration of commands, and a header cell `Declared` an enumeration of the project's declarations, with the version in the `Value` cell beside it. A `Command` row names one target, written `make <target>`; a `Declared` row reduces to its text, a link to its label and a code span to its code, and a package name is compared as the packaging ecosystem compares one. The comparison runs in both directions, so a dependency dropped from the project stops being documented and a target added to the `Makefile` is documented before it lands. No target is excluded: `make check` is named by a table like every other, and the only names the check passes over are make's own dot-prefixed directives, which are not commands. A passing run prints every target and declaration it compared, so the set it read is visible rather than implied.

`invocation.py` holds the documented invocation to the command that offers it. It reaches the build the same way the corpus does — `PROSIFORM_BUILD` names its command line, read through `runner.py` so one function reads it for both — and compares the README's tables with the build's own `--help` output in both directions: an argument the command offers and no table names is one a caller never learns of, and a row the command does not offer is a command line that fails for whoever follows it. Each row reproduces the argument's or the status's own help text word for word, runs of whitespace aside, so a default that moves is a row that stops matching. The profile identifier comes from `--version`, because the help output does not carry it. Three further things the contract requires of the documented invocation — that a failed run stops the work, that reading the sources instead is unsupported, and which platforms the build supports — are prose rather than a surface the command exposes, so each is held to the sentence that states it: the check keeps the statement from being dropped, and the review that lands it is what holds it true. Tables are located by their headers and the statements by their section's heading, so the documentation moves within a README without the check being edited.

`vocabulary.py` takes the contract's term inventory from the contract itself: the design italicises a term where it first uses it, and the glossary must define each one. It reads the design and the epic criteria from the branch and path the README's Design link names, which a checkout reaches as `origin/engineering`, so no path into a dated planning folder is written in a check. Superseding that folder changes the README's link, and `links.py` holds that link to resolving.

`independence.py` holds the corpus and its report to the behaviour rather than to a build. It scans the claims and not the documents under test: every string a manifest declares and the fixture's own identity, and the conformance report as it renders, which brings the design's clause names and the declared surface under the same rule. A fixture's source tree and the bytes it expects back are the input a run consumes and the output it reproduces, so a corpus bundling real documents that name real source files keeps its realism. The inventory is three kinds of term — an implementation language or runtime, the machinery of modules and packaging with the source-file paths and reserved identifiers beside it, and the wording a build's fault reporting uses in place of the contract's codes — and each term states what it names, so a hit reads as the reason it is refused.

The contract's own declared names are interface terms, and they are held apart from that inventory rather than subtracted from each scanned text. The error codes, the warning codes and the exit statuses come from the manifest schema and the options from the tables the documented invocation enumerates them in, and the check scans those names themselves: one matching the inventory fails the run. The two sets are then disjoint by the check's own verdict, the scan needs no exclusion list that could drift, and a contract coming to declare an implementation term is reported rather than quietly admitted.

`manifests.py` takes the code catalogues from the schema and the schema from the corpus, so a code is declared once and read from that declaration wherever it is used. A diagnostic's severity selects its catalogue — an error decides a failing run and a warning accompanies a successful one — so neither admits the other's codes. A test holds each catalogue to the design's own text, collecting every code the design carries under the prefix that severity uses, `E_` for an error and `W_` for a warning, and requiring the schema to enumerate exactly those. `declared_codes` reads the other direction, collecting the codes the corpus's own manifests carry at one severity, and a test requires every code in the warning catalogue to be among them: a warning accompanies a successful run, so a declared warning no fixture states is a claim about standard error that no run of the corpus exercises.

The suite holds each check's reading of its own input: the documents discovery finds, the references and heading fragments the link check resolves, the targets and declarations the table check compares, the marked terms and glossary definitions the vocabulary check compares, the tree listings the layout check reads, and the responses the smoke run gets back from the installed command. Each case supplies input the parser would read wrongly rather than the repository's own documents, where every parse happens to be correct.

The heading-slug rule is held to GitHub's own anchors. [`tests/anchors.json`](tests/anchors.json) carries a document of headings and the anchor ids GitHub generated for it, captured in one call to the Markdown API, and the suite feeds those same bytes to the link check's fragment reader. The oracle is GitHub rather than an expectation written here, and the comparison is a command the suite runs rather than an observation at a revision. Refreshing it is that one call against the captured document, the `id` attributes of the response read in order with their `user-content-` prefix removed.

The scripts are linted, formatted and type checked with the Python build's tools, which `make lint`, `make format-check` and `make typecheck` run over `checks/` alongside the package.

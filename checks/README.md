# Checks

The checks that hold the repository's own claims true. Each has a named command in the [Makefile](../Makefile) that runs it from the repository root and returns a nonzero status when it fails, so a developer and a continuous-integration job invoke the same name.

| Check | Command | Asserts | Fails on |
| --- | --- | --- | --- |
| `layout.py` | `make layout` | The repository holds a tree for the fixture corpus, one for the Python build and one for documentation. | A tree that holds no tracked file. |
| `links.py` | `make links` | Every reference every document the repository owns carries resolves, the fixture corpus excepted. | A path that does not exist, a fragment no heading generates, a git ref or path absent from the engineering branch, or a remote address that does not answer. |
| `tables.py` | `make tables` | The README tables that enumerate the repository's commands and the project's dependencies name exactly what the `Makefile` and `prototype/pyproject.toml` declare. | A target or a dependency no table names, a table row naming a target or a dependency the project does not declare, or a row naming a version the project does not pin. |
| `vocabulary.py` | `make vocabulary` | The shipped glossary and the contract carry one vocabulary between them. | A term the design marks as a contract term and `docs/glossary.md` does not define, a marked term the glossary names as deliberately not used, or a definition neither the design marks nor an acceptance criterion uses. |
| `manifests.py` | `make harness` | Every fixture the corpus holds is a fixture the manifest schema describes. | A manifest leaving out one of the five declarations, carrying a field the schema does not describe, naming a code outside the catalogue its diagnostic's severity selects, or naming a path the fixture does not hold. |
| `runner.py` | `make harness` | A fixture's run against the build under test produces the result its manifest declares. | A differing exit status, standard output differing in any byte, or a diagnostic missing, extra, out of order, or carrying another value in a field the manifest declares. |
| `corpus.py` | `make corpus` | Every fixture the corpus holds produces, against the build under test, the result its manifest declares. | A fixture whose run differs from its manifest, a fixture awaiting later work that meets its manifest instead, or no build configured. |

`make check` runs these seven alongside the Python build's tests and static checks, in one pass over the repository.

`layout.py`, `links.py`, `tables.py` and `vocabulary.py` are standalone Python 3 scripts with no dependency beyond the standard library, run under `python3` directly. `manifests.py` and `runner.py` are the corpus's own modules rather than commands of their own, and `make harness` runs the suite in [`tests/`](tests) that exercises both. `corpus.py` is a command, run from the locked environment because it reads those two modules. `documents.py` is a module too: it holds the documents the checks read and the reading they share, so one discovery serves both, `links.py` reading every document and `tables.py` the READMEs among them, which is where the project's command and dependency tables sit.

`manifests.py` is the manifest reader and validator: it reads [`fixtures/manifest.schema.json`](../fixtures/manifest.schema.json) through `jsonschema` from the locked development group and applies it to every fixture. `runner.py` reads its validation from that same module, so a manifest is checked the same way wherever it is read.

`runner.py` runs one fixture. It reads the manifest, invokes the build under test against the fixture's source tree, and compares the run's standard output, exit status and diagnostics with what the manifest declares. The build is named by configuration — the environment variable `PROSIFORM_BUILD` holds its command line — and invoked as a subprocess, so the module imports no package, names no module and names no language, and the production build runs the same corpus through a runner of its own. There is no default build: an unset variable raises rather than returning a verdict, so a fixture is never reported as holding against a build that never ran. The runner supplies the allowed source root and asks for diagnostics as data, which the contract's command line spells `--root DIR` and `--diagnostics json`, so a code is compared as a value rather than as prose.

A mismatch names the expectation that differed and locates the difference inside it. Standard output is compared as bytes and reported by byte offset, line and column, each window spelling its control bytes, so a CRLF against an LF reads as a difference rather than as two identical lines. Diagnostics are compared in order on the fields the manifest declares: one missing, one extra, a pair in the wrong order, and a field carrying another value are each reported as what they are, and a diagnostic carrying more than the manifest declares matches. `PROSIFORM_BUILD_TIMEOUT` bounds a run in seconds, and a run that exceeds it fails the fixture.

`corpus.py` runs the whole corpus. It walks every fixture `manifests.py` discovers, in path order, puts each through `runner.py`, prints a line for each so the set it ran is visible, and returns a nonzero status when one of them fails. A failing fixture is named by its identity — its path under `fixtures/` — and its differences are printed under it, so a red run names which fixture rather than saying the corpus failed. A build it cannot reach fails the run: a corpus run that skips because nothing is configured sits inside a passing suite saying nothing.

The corpus declares the contract, and the contract runs ahead of any one build, so a manifest may name the work that delivers what it expects with `awaiting`. A fixture carrying that marker and failing is reported as awaiting that work and leaves the run green; one carrying it and meeting its manifest fails the run, so the marker is lifted on the change that makes it untrue rather than outliving the work it waits on. The marker sits in the manifest beside the expectation it qualifies, because a list of exceptions held anywhere else drifts from the fixtures it names in both directions.

`documents.py` finds a document the way `layout.py` finds a tree: git tracks it. Nothing lists the documents, so a document added later comes into the checks by being committed, and neither check is edited. The fixture corpus is excepted, and the exception is the corpus rather than a list of names: a fixture is a directory holding a manifest, which is what `manifests.py` calls one, and git lists those manifests alongside the documents, so a fixture added anywhere is excepted. A fixture's source deliberately carries references a run is meant to refuse and its expected bundle is output rather than a document a reader follows, so resolving either would fail by design. [`fixtures/README.md`](../fixtures/README.md) sits above every fixture rather than inside one, so it is read like any other document. `documents.py` also blanks fenced blocks before a document is read and parses its pipe tables, so an example inside a fence is never mistaken for a reference or a row.

`links.py` reads every document `documents.py` finds, and reaches addresses outside this repository only with `--online`, which the named command supplies: without the flag a remote reference counts as unresolved, so an offline run cannot pass. References into this repository's own branches resolve through git, so they need no network. An issue, a pull request or a project board is read through `gh api` with the caller's credentials, because a private repository answers an unauthenticated request with 404. Naming documents on the command line checks those instead, which is for reading one document while editing it.

`tables.py` locates a table by its header rather than by the document or the section it sits in: a header cell `Command` makes a table an enumeration of commands, and a header cell `Declared` an enumeration of the project's declarations, with the version in the `Value` cell beside it. A `Command` row names one target, written `make <target>`; a `Declared` row reduces to its text, a link to its label and a code span to its code, and a package name is compared as the packaging ecosystem compares one. The comparison runs in both directions, so a dependency dropped from the project stops being documented and a target added to the `Makefile` is documented before it lands. No target is excluded: `make check` is named by a table like every other, and the only names the check passes over are make's own dot-prefixed directives, which are not commands. A passing run prints every target and declaration it compared, so the set it read is visible rather than implied.

`vocabulary.py` takes the contract's term inventory from the contract itself: the design italicises a term where it first uses it, and the glossary must define each one. It reads the design and the epic criteria from the branch and path the README's Design link names, which a checkout reaches as `origin/engineering`, so no path into a dated planning folder is written in a check. Superseding that folder changes the README's link, and `links.py` holds that link to resolving.

`manifests.py` takes the code catalogues from the schema and the schema from the corpus, so the one declaration of a code is the one both builds read. A diagnostic's severity selects its catalogue — an error decides a failing run and a warning accompanies a successful one — so neither admits the other's codes. A test holds each catalogue to the design's own text, collecting every code the design carries under the prefix that severity uses, `E_` for an error and `W_` for a warning, and requiring the schema to enumerate exactly those.

The scripts are linted, formatted and type checked with the Python build's tools, which `make lint`, `make format-check` and `make typecheck` run over `checks/` alongside the package.

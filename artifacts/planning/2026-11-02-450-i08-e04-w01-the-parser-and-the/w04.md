**Component:** main:fixtures/README.md

## Overview

The corpus states a fault as a manifest field, and the page says the runner asks for it by the means the design declares, naming no command-line spelling.

## Problem

The page described the fault in terms of the option.

- **The field's row named the option.** `fault` read "which the runner asks for as `-x NAME`".
- **The fault section named it.** "the contract declares `-x NAME` for a conformance run to reach them".
- **The runner section named it.** "appends `-d json`, and `-x` where the manifest names a fault".
- **The schema named it.** `manifest.schema.json`'s `fault` description said "the contract's `-x NAME`".
- **The refusal needs a fixture value.** The schema admits only the three faults, so a fixture stating an unrecognized one has no value to declare.

## Proposal

**The scene.** `fixtures/README.md` documents each manifest field, and `manifest.schema.json` validates a manifest.

**The design.**

- **The pages state a behaviour.** The field row, the fault section and the runner section say the runner asks for the fault by the means the design's Conformance faults section declares, linking it, and name no flag.
- **The schema names one value for the refusal.** `unrecognized` joins the enum, described as a fault the contract does not name, which the run refuses as invalid usage. Every other value outside the set still fails validation, so a mistyped fixture fault is caught.
- **The fault table gains a row** for `unrecognized`, and the list of fixtures declaring a fault names the new one.
- **The `E_INVALID_USAGE` table gains a row** for the new fixture, and its count reads eight.
- **The bare command depends on arguments alone**, in the schema's `arguments` description as in the runner.

## Overview

Each operator is its mark followed by a space; a mark with no space after it is link text.

## Problem

- **Arrow-led link text.** pf read `⇉` and `¬` as operators with or without a following space, so link text that happens to start with either character was withheld from the run.

## Proposal

- **Recognition.** `closure.opens(text, at)` holds where an operator mark sits at `at` and U+0020 follows it. `operators` skips blanks, then reads operators while `opens` holds; the first mark with no space after it ends them. `unmarked` strips a deferral only where `opens` holds, taking the blanks after it.
- **Combinations.** `[¬ ⇉ X]` and `[⇉ ¬ X]` carry both operators and are refused with `E_UNSUPPORTED_CONSTRUCT`. `[¬⇉ X]` and `[⇉¬ X]` carry none and are ordinary links. `[¬  ⇉X]` defers and publishes `⇉X`.
- **Blanks.** Only a space opens an operator: `¬` followed by a tab is link text. After the opening space, further blanks (spaces or tabs) are the operator's spacing and are removed with a deferral mark.

## Implementation Findings

- **Fixtures added.** `dispatch/a-dispatch-mark-with-no-space-after-it-opens-an-ordinary-link` and `deferral/a-deferral-mark-with-no-space-after-it-opens-an-ordinary-link`: the target is compiled, the destination is rewritten to the bundled heading, the mark is kept, and no diagnostic is raised.
- **Existing marks.** No fixture source, expected bundle or example document carried an unspaced mark in link text, so no corpus output changed. The `⇉` and `¬` in code spans (`example/work-planner/bootstrap.md`, `example/work-tracker/SKILL.md`, and their copies in usage-example bundles) name the mark in prose and are not link text.
- **Tests rewritten.** `test_cli.py` (blanks after the mark), `test_bundle.py`, `test_derived_output.py`, `test_file_roots.py`, `test_rewrite.py` and `test_source_metadata.py` wrote deferrals as `[¬B]`; each now writes `[¬ B]`. One span test in `test_rewrite.py` keeps `[¬rules]`, since it reads spans only.

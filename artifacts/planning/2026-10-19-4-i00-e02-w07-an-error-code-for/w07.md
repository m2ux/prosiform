## Overview

An error code for every failing outcome the contract names, so the corpus can declare each one.

## Problem

The contract declares twelve error codes, each naming a defect in a source document or in the closure drawn from it. It names none for a fault in the command line itself other than a grouping rule, and none for an unexpected internal error, although it declares an exit status for both.

A diagnostic carries the stable code of the defect it reports. A failing outcome the contract names no code for therefore emits a diagnostic carrying a severity and a message and no code, since a code is the name of a defect the contract declares and inventing one puts a name in the tool that the contract does not carry.

A fixture's manifest requires a catalogued code for every diagnostic it declares. So the outcomes with no code are outcomes the corpus cannot state: a missing allowed source root, an unknown diagnostic format, an output path naming an input source, a fragment-only reference with no referring document, and an internal failure are each reachable, each declared an exit status, and each outside the corpus. The contract has behaviour its own conformance instrument structurally cannot reach.

Three of those outcomes are refusals the profile itself makes, and each is the refusing direction of an epic criterion: raw HTML in selected content, a construct recognized as an unsupported dependency or section-naming extension, and an entry reference whose suffix lies outside the profile. A criterion whose refusing direction no fixture can declare is a criterion the corpus verifies in one direction only, and unit tests carry the other, which binds that direction to one implementation.

## Proposal

The contract declares a code for each failing outcome it names, and the manifest schema's catalogue carries them, so the corpus can declare any outcome the contract declares.

The two documents are held in exact agreement by the catalogue test, which reads the design from the engineering branch and the catalogue from the schema. They therefore change as one piece of work: the design gains the codes, the schema's catalogue gains the same codes, and the fixtures that could not exist before are written against them.

A usage failure takes a code naming the fault in the command line, not the document the command line mentions, so a caller reading the code is not sent to look at its sources. An internal failure takes one code of its own, which the contract already forbids being reported as a source-document defect.

### None of Them Is Covered by a Code the Contract Already Declares

W02 found that two outcomes it had taken for uncoded were already named — `E_SOURCE_OUTSIDE_ROOT` for a reference normalizing outside the root, and `E_TARGET_NOT_FOUND` for one naming no document under it — so every outcome above is checked against the twelve before a new code is written. Each of the three near misses is a different defect from the code it resembles.

- **An entry suffix outside the profile is not `E_TARGET_NOT_FOUND`.** That code names a local Markdown reference resolving to nothing. A `.txt` entry names a document that is very often there; the profile refuses to classify it as Markdown. Reporting it as a missing target sends the caller to look for a file that exists.
- **An allowed source root naming no directory is not `E_TARGET_NOT_FOUND` either.** The root is the confinement boundary the run is given, not a Markdown target the run resolves, and no reference has been read when it fails.
- **Raw HTML in selected content is not `E_UNSAFE_BUNDLE_BOUNDARY`.** That code names an output defect: a combined region absorbing later material into a container it does not belong to. Raw HTML is refused on the way in, before any boundary exists.

So each outcome needs a code the contract does not yet declare. They do not each need a *distinct* one.

### A Usage Failure Takes One Code

Five of the outcomes are faults in the command line, and they take one code, `E_INVALID_USAGE`, between them. The alternative was one code per fault.

- **A code exists so a caller can act, and every usage fault leads to the same action.** Read `--help` and correct the command line. A set of codes that all resolve to one remedy names a distinction the caller cannot use; the message is what says which fault it was, and the contract requires a message and a remedy on every diagnostic.
- **The faults are not enumerable from the contract.** A command line can fail the grammar in as many ways as the grammar has surface: an unknown option, an option missing its argument, a value outside a declared set. One code per fault would make the catalogue a function of the argument parser rather than of the contract, and would grow every time an option is added.
- **The contract already separates a code from a status**, so `E_INVALID_GROUP_RULE` is not an exception to this and is left exactly as it is. It names a defect in a grouping rule's *value*, which is why it decides exit 2 for a malformed or repeated rule and exit 1 for a slug naming no directory. `E_INVALID_USAGE` names a defect in the command line's *form*. The two do not overlap: the grammar admits `--group SLUG:DEPTH`, and the rule's content is read afterwards.

### The Codes, and the Clause Each Is Declared Under

Nine codes, each written into the clause that states the outcome. The design declares its codes inline at those clauses and holds no list of them, and that habit is followed rather than replaced.

| Code | Clause | Outcome | Status |
| --- | --- | --- | --- |
| `E_INVALID_USAGE` | CLI contract | A command line the contract's grammar does not admit | 2 |
| `E_ROOT_NOT_FOUND` | CLI contract | The allowed source root names no directory | 1 |
| `E_UNSUPPORTED_ENTRY_SUFFIX` | Markdown and source-heading profile, File suffixes | An explicit entry whose suffix is outside the profile | 1 |
| `E_RAW_HTML` | Markdown and source-heading profile, HTML | Raw HTML in selected content | 1 |
| `E_UNSUPPORTED_CONSTRUCT` | Markdown and source-heading profile, Unsupported extensions | A recognized unsupported dependency or section-naming construct in selected content | 1 |
| `E_PUBLICATION_FAILED` | Validation and failure contract, Publication | A destination that refuses the write, a broken pipe among them | 3 |
| `E_UNEXPECTED_INTERNAL_ERROR` | Exit status and JSON diagnostics | An unexpected internal error | 4 |
| `E_INVALID_ENCODING` | Markdown and source-heading profile, Encoding | A source that is not valid UTF-8 | 1 |

`E_INVALID_ENCODING` is the ninth, and it arrives with the base rather than with the brief: W03 landed the encoding requirement as `#50` while this row was in flight, and it left the failure uncoded rather than inventing a name, as the contract requires of a defect it does not declare. It is a failing outcome the contract names at its Encoding clause, so it is inside this row. AC8 reads *a source that is not valid UTF-8 fails rather than being decoded with replacements, as the encoding fixtures show*, and a manifest requires a catalogued code for every diagnostic it declares, so without this code AC8 has no fixture that can state it.

`E_RAW_HTML` and `E_UNSUPPORTED_CONSTRUCT` stay two codes rather than one *outside the profile* code, because they are two clauses with two remedies: HTML is rewritten as Markdown, and an unsupported construct naming a dependency is rewritten as a Markdown link. A caller reads the remedy from the code.

### The Order the Two Documents Change In

The catalogue test asserts the schema's catalogue equals the set of codes the design carries, and it reads the design from `origin/engineering` rather than from the branch under test. The two halves therefore cannot both hold at any single moment across two branches, and the order is a decision this row takes rather than an accident of what is edited first.

1. The schema, the command and the fixtures land on the task branch, and every check but the catalogue test is green locally. The design is not pushed.
2. The design's codes are pushed to `engineering`. From this moment any continuous-integration run on any branch fails the catalogue test, because every branch's schema is one the design no longer matches.
3. The task branch is pushed, its run passes because its schema and the design agree, and it merges.

The window is between the second step and the third, it is bounded by the implementation already being finished before it opens, and its timestamps are recorded in `validation.md`. A branch that has not yet taken this schema fails the catalogue test inside the window, so a red run there is this change arriving rather than a fault in that work; it goes green when the base carrying this schema reaches it.

The sequence runs twice, because the base updated between them: once for the eight outcomes the row was planned with, and once for the encoding failure W03 landed while the row was in flight. Each window is the same shape and the same six seconds wide.

### The Fixtures That Become Possible

Seven of the outcomes become fixtures, and each declares a failure rather than a success, so each passes against the build as it stands rather than waiting for the emitter W04 delivers.

| Fixture | Code | Status |
| --- | --- | --- |
| `cli/diagnostics-format-unknown` | `E_INVALID_USAGE` | 2 |
| `cli/output-naming-an-input-source` | `E_INVALID_USAGE` | 2 |
| `cli/fragment-only-reference-without-from` | `E_INVALID_USAGE` | 2 |
| `profile/entry-suffix-outside-the-profile` | `E_UNSUPPORTED_ENTRY_SUFFIX` | 1 |
| `profile/raw-html-in-selected-content` | `E_RAW_HTML` | 1 |
| `profile/unsupported-construct` | `E_UNSUPPORTED_CONSTRUCT` | 1 |
| `profile/source-not-utf8` | `E_INVALID_ENCODING` | 1 |

Five outcomes take no fixture, and each for a reason in the runner or the contract rather than in the catalogue.

- **A missing `--root` and a root naming no directory.** The runner resolves the fixture's source tree and supplies `--root` itself, and a manifest's `invocation.root` is required to be a directory, so neither fault can be written into a manifest.
- **An invocation naming no entry reference.** Reachable, and it declares nothing the three usage fixtures above do not already declare: the same code, the same status, the same empty bundle.
- **A write the output stream refuses.** The runner reads both streams to completion, so a broken pipe is not reachable through it.
- **An unexpected internal error.** A fixture declaring exit 4 would state a property of this build rather than of the contract, and W04 would delete it. W01 recorded that reasoning and it is unchanged by the code now existing.

### What the Command Carries

Each diagnostic that currently carries no code carries the code its outcome declares. Nothing about the statuses changes: the mapping W01 recorded is what the codes are attached to, and the placeholder exit 4 for a run whose sources parse keeps its status and now names `E_INTERNAL_ERROR`, which says the build cannot carry the request out rather than that a source is defective.

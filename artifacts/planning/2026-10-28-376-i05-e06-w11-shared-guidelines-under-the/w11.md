**Component:** example/guidelines.md

## Overview

The shared skill guidelines at `example/guidelines.md` agree with the work-planner example's authoring rules, so a reader of the example meets one rule for commands and rule homes, not two that disagree. Each shared rule the work-planner guidelines retire is restated generically, since the shared file serves every skill under `example/`. Names and paths outside this repository leave the file.

## Problem

The shared guidelines apply alongside the work-planner example's own guidelines, and still state the shape those guidelines retire.

- **Commands.**
  The shared Commands section places each command specification in a `## Commands` section at the end of the file whose procedure runs it, keeps a catalog for commands with several callers, and names a specification from prose by link. The work-planner Commands in steps rule places each command in an unindented fenced block in the step that runs it, with no Commands section, and writes a shared helper in each operation that runs it.
- **Procedure files.**
  The shared Procedure files section lists Commands among a procedure file's top-level sections, and takes its definition of a procedure from the Commands section.
- **SKILL.md structure.**
  Its Commands entry states that SKILL.md holds no command of its own, a case the commands rule already settles.
- **One home per rule.**
  The shared rule homes each rule in SKILL.md, the owning mode or a shared guide. The work-planner rule homes it in the contract it constrains, the step it binds, or a rules or conventions entry when it binds every mode.
- **Surviving references.**
  The Links section places conventions ahead of the procedures and commands they govern, and Progressive Disclosure selects checks before retrieving their command specifications.
- **Outside names.**
  The Prerequisite citation example, the Files › Shared entry and the Changes › Verified entry name files and paths outside this repository.

## Proposal

A skill author reading `example/guidelines.md` and then a skill's own guidelines meets no rule in one that the other retires.

### Rules and Replacements

| Shared rule | Replacement | State or link |
| --- | --- | --- |
| Commands › One spec per operation | Retired: a command is not a sub-section of its own | Removed |
| Commands › Local to the procedure | Commands in steps: a command sits in the step that runs it, in an unindented fenced block, never a code span; no file has a Commands section; the step states where the command runs from and which inputs fill its parameters; a command several procedures run is written in each step | State generically |
| Commands › Local to the procedure: catalog, caller, two owners | Retired with the specification they placed | Removed |
| Commands › Local to the procedure: prose runs nothing | Kept as Prose runs nothing | State generically |
| Commands › Local to the procedure: definition of a procedure | Moved to Procedure files, where the definition is used | State generically |
| Commands › Spec layout | Folded into Commands in steps: the step's instruction precedes the block | State generically |
| Commands › Named by link | Retired: no specification exists to link | Removed |
| Commands › Conventions | Skill-wide prerequisites stay in the conventions file; a condition governing one command sits in the step that runs it | State generically |
| Procedure files › Top-level sections | Procedure, Reference and Rules | State generically |
| SKILL.md structure › Commands | Removed; Commands in steps settles it | Removed |
| Prose › One home per rule | Home: the contract or outcome it constrains, the step it binds, a rules or conventions entry when it binds every mode, or the guidelines when it governs how a file is written; every other file links it | State generically |
| Links › Prerequisite citation | Conventions sit ahead of the procedures they govern; the example names a generic file | State generically |
| Progressive Disclosure › Applicability | Select a check before reading the steps that run it | State generically |
| Files › Shared; Changes › Verified | Name the shared folder and the shared skill check by role, with no path outside this repository | State generically |

### State or Link

Every rule above is stated generically rather than linked to the work-planner guidelines. The shared file serves every skill under `example/`, and the work-planner guidelines link the shared file as their base; a shared rule that took a skill's guidelines as its authority would invert that dependency, and bind another skill to work-planner's file. The work-planner rules keep what is specific to that skill, such as the next step reading a command's exit code and one command per block.

### Bindings and Conventions

The shared file states no repository, label, board field or per-deployment limit; its character, line and length limits are fixed style rules. It restates neither helper invocation nor write confirmation. Nothing is linked or removed on this account.

### Fixtures

The one usage example reaching the shared file, the Revise mode's, keeps its authored links to it, which resolve outside the bundle's root and carry no content. Its bundle is regenerated and compared; the `#commands` anchor it links stays.

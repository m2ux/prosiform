**Component:** evals/diagram-following/workflows

## Overview

The workflows the eval gives to agents: synthetic, of graded difficulty, each in three forms, each with scenarios whose correct path is exact.

## Problem

No workflow exists that an agent can be asked to follow and whose correct execution is known in advance, so nothing can be scored.

## Proposal

A workflow is a source tree whose entry document holds a `mermaid` `stateDiagram-v2` or `flowchart`, each state a node whose click links that state's section.

- **Graded difficulty.**
  `linear` — four states in sequence. `branching` — a decision on an input chooses one of two paths that rejoin. `looping` — a review state returns to rework until an input-driven condition holds, and one state is reached through a link inside another state's section rather than from the diagram.
- **What a state's section says.**
  The action to take — write `actions/<state>.txt` with stated content — then how to choose the next state from the files under `inputs/`. Every section ends by naming the transition rule; terminal states say the workflow is complete.
- **The trace.**
  The task instruction, shared by every form, tells the agent to append `<state>` as a line to `trace.log` on entering each state. The trace and `actions/` are what the scorer reads.
- **Three forms.**
  `diagram/` — the source tree with the diagram, bundled by `pf` for the bundle form and given as-is for the tree form. `prose/` — the same state sections, where the diagram is replaced by prose transitions; bundled by `pf`.
- **Scenarios.**
  `scenarios.toml` per workflow: each scenario's input files and its expected path. Two scenarios per decision state, so every branch and loop count is exercised.
- **Checks.**
  Tests run by `make check` bundle each form, compare the prose and diagram forms' sections, and walk each expected path against the diagram's edges. The repository's layout check admits `evals/`.

## Work Breakdown

| Part | Description |
| --- | --- |
| Analysis | Read the epic, the specimen fixture, `checks/layout.py` and how `checks/tests` run. |
| Plan | Diagram: a Mermaid `flowchart` (clicks are flowchart syntax); node ids are state names, `start(( ))` points at the first state and each terminal state points at `stop((( )))`. Section template: `# <State>`, the action `Write actions/<state>.txt containing <value>.`, then one `**Next.**` paragraph — the only part the forms differ in. The diagram form names an edge label (`take the transition labelled ...`) or takes the one edge out; the prose form names the next state as a link; a terminal says `The workflow is complete.` A condition is either `inputs/<file> reads <value>` or `trace.log holds the line <State> fewer times than the number in inputs/<file>`. Edges and the terminal set have one source of truth: the Mermaid source, parsed by `evals/diagram-following/workflow.py`; `scenarios.toml` names only each scenario's inputs and path, and the AC3 test holds the path to the parsed edges and to the walk both forms' sections determine. `instruction.md` holds the shared task text with `ENTRY` standing for the document a session reads. Tests sit beside the reader (`test_workflow.py`), run by `make harness`, and bundle with the `pf` the locked environment installs; `evals` joins the lint, format, typecheck and layout checks. |

**Component:** evals/diagram-following

## Overview

States the `bootstrap` form in the diagram-following eval's README beside the six forms it already describes, with the `--forms` default the runner takes, and adds a test holding the README's form table and that default to `run.FORMS`, so a reader running the eval learns every form a run can give and the two cannot drift apart again.

## Problem

`run.py` maps seven run forms in `FORMS`, `bootstrap` among them, and `--forms` defaults to all seven. The README says a session receives one of six forms, its Forms table has no `bootstrap` row, and its `--forms` row gives a default without `bootstrap`. Nothing states what the `bootstrap-audit` workflow measures, that its session finds a skill rather than an entry document and compiles it with `pf`, which harness can run it, or the `unbootstrapped` class a session that skips the compile takes. The runner's module docstring lists four forms. Nothing reads the README against the runner, so the gap opened silently when the form was added.

## Proposal

A reader opens the README to choose the forms for a run. The Forms table lists every form `run.FORMS` names, in its order, and the `--forms` row gives the default `run.py` builds from it.

- **Forms.**
  The table gains a `bootstrap` row: a skill placed where the agent CLI discovers skills, naming the diagram form's sources it compiles with `pf`. What it isolates is whether an agent compiles a workflow before following it. The intro states the form count by the table rather than a number, and the paragraph naming which workflow takes which forms adds `bootstrap-audit`.
- **Bootstrap scenario.**
  A subsection beside Dispatch scenarios states what `bootstrap-audit` measures, that its session runs `pf` and so needs a harness with a shell (Cursor or opencode, not Claude), and that its scenarios carry a dispatch trace held as the dispatch scenarios' are.
- **Scoring.**
  The class table gains `unbootstrapped`: a session that walked the path without running `pf`.
- **Harness names.**
  The Login text and `--harness` row name the three harnesses `HARNESSES` declares, since the bootstrap form is defined by which of them can run it.
- **Default matrix.**
  The default-matrix paragraph counts the scenarios and workflows the Claude harness runs, which excludes the bootstrap form.
- **Runner docstring.**
  `run.py`'s module docstring lists every form.
- **Check.**
  A test in `test_run.py` reads the README's Forms table and `--forms` row and asserts the table's forms are `run.FORMS` in order and the default is `",".join(FORMS)`.

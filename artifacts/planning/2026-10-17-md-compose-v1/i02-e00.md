## Overview

The parser verdict answers, with executed reproducers against a pinned parser version, whether that parser can supply what the design requires: access to every reference-definition occurrence, and an observable signal when an internal limit suppresses a reference lookup. The epic ends with a report stating each gate's answer and the evidence behind it, and a recorded route for any gate the parser fails.

## Problem

The production build rests on parser capabilities that have been inspected in source but never executed.

- **A definition map holds one occurrence per label.**
  The inspected first pass inserts definitions with a first-wins entry, so a later duplicate occurrence becomes no map entry, and removing every definition from emitted content requires finding occurrences the map does not hold.

- **A suppressed lookup is indistinguishable from literal text.**
  The inspected lookup returns nothing once its reference-expansion budget reaches zero, before definition lookup and before broken-link handling, so a reference the limit suppressed and brackets that were never a link arrive identically.

- **A retained definition does not imply enumerable duplicates.**
  Exposure of the winning definition map is evidence about resolution, not about occurrence coverage, so the gate cannot be answered by reading that interface.

- **Agreement between two parses proves nothing about omission.**
  An event stream that omits a suppressed reference omits it consistently, so a second parse agrees with the first and the omission stays invisible.

- **An upstream fix of unknown reach.**
  An offset-iterator defect on definition-bearing list items is reported upstream with a fix described on the project's main line, and which released version carries it has not been established here.

## Proposal

- **Each gate gets an executed reproducer.**
  One constructs sources carrying later duplicate definitions, case-fold-equivalent labels, unused definitions, multiline definitions and supported container contexts, and records what the pinned parser's public interface exposes for each. One drives reference-expansion suppression below the tool's declared input and output limits and records whether the suppression is observable.

- **A budget exhausted on a final successful reference is a distinct case.**
  The suppression reproducer includes a source whose last valid reference consumes the budget with no later lookup, because reporting that as an omission would fail runs that omitted nothing.

- **The reported offset-iterator defect is executed, not assumed.**
  Its reproducer runs against the pinned version, and the result is recorded against the existing upstream report rather than becoming a new one.

- **Resource protections stay on.**
  No gate is answered by disabling a parser limit. A reproducer that would need that records the gate as unsatisfied.

- **A failed gate takes a recorded route.**
  Parser-aware occurrence collection, narrowly scoped instrumentation, a different parser candidate and a separate upstream proposal are the routes. The route taken is written into the report as a decision with its reasoning.

## Acceptance Criteria

- [ ] **AC1.** A reproducer records, for sources carrying later duplicate definitions, case-fold-equivalent labels, unused definitions, multiline definitions and supported container contexts, which occurrences the pinned parser's public interface exposes, as its recorded run shows.
- [ ] **AC2.** A reproducer drives reference-expansion suppression below the tool's declared input and output limits and records whether that suppression is observable through the pinned parser's public interface, as its recorded run shows.
- [ ] **AC3.** A source whose final successful reference exhausts the budget with no later lookup is recorded as carrying no suppression, as the reproducer's recorded run shows.
- [ ] **AC4.** The offset-iterator behaviour reported upstream for definition-bearing list items is executed against the pinned version and its result recorded, as the reproducer's recorded run shows.
- [ ] **AC5.** The gate report states, for each gate the design names, whether the pinned parser's public interface satisfies it, with the executed evidence establishing that answer.
- [ ] **AC6.** A gate the pinned parser fails carries a recorded route decision naming one of parser-aware collection, scoped instrumentation, a different parser candidate or a separate upstream proposal, with the reasoning for it.

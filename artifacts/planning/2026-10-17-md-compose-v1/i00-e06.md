## Overview

The validation gate stands between a constructed candidate and a published composite. The candidate is reparsed under the declared profile and checked against the provenance recorded during construction; sources are rechecked for change; a generated document is refused as input; and every failure produces a diagnostic a calling agent can act on. Nothing reaches standard output until the whole candidate passes.

## Problem

A composite can be syntactically valid Markdown and still be the wrong document.

- **A boundary can swallow what follows it.**
  Two regions joined without safe separation can place later content inside an earlier code fence, HTML block, list or quote, which changes meaning without producing invalid Markdown.

- **Surface validity proves nothing about provenance.**
  A reparse that agrees with itself establishes that the output parses, not that each region came from the source it claims, nor that a region is missing.

- **A source can change mid-compilation.**
  Files are read during discovery and published after validation, so a source edited in between would be published from the bytes discovery captured rather than the bytes on disk.

- **Output read back as input compounds.**
  A published composite already carries generated file headings and hierarchy-path links, so composing it again would rewrite generated structure as if it were source.

- **A failure the agent cannot explain is a failure twice.**
  Without a code, a location, the offending reference and the chain that reached it, a calling agent can report only that composition failed.

## Proposal

- **Candidate validation has its own policy context.**
  The candidate is reparsed under the same grammar but expects generated filename headings, shifted headings and scaffolds. It is not passed back through frontmatter stripping, dependency discovery or generated-input rejection.

- **Invariants are checked against recorded provenance.**
  Destination integrity, exactly-once coverage, absence of new links, absence of surviving definitions, ownership stability, outline preservation and depth safety are checked against the provenance ranges and generated-structure records kept during construction, not by counting strings.

- **Boundaries are proven safe.**
  Emitted regions are separated and the result reparsed. A boundary that absorbs content into an unintended container fails with its declared code, naming the source regions and the conflicting boundary.

- **Sources are rechecked before publication.**
  Each source is compared against its captured content hash and canonical identity. A changed, removed or relocated source fails with a retry message.

- **A generated document is refused as input.**
  A source whose links carry composite destinations is rejected anywhere those links appear, recognized by a fragment whose first segment names a document path, while a destination-like fragment inside code is not detection.

- **Validation follows the selection, not the file.**
  Link resolution, self-reference and syntax checks apply within the selected dependency closure. Parsing a whole file to index it does not make its unselected sections dependencies, so a broken or self-referential link in one of them does not fail a composition that did not select it. If closure later includes that section, its links become subject to validation like any other.

- **An indexing failure is not a dependency.**
  A file-wide parsing-safety limit exceeded by an unselected construct fails as an inability to index that source safely, diagnosed as such rather than as a dependency on the construct that exceeded it.

- **Diagnostics carry a stable shape.**
  Each carries an error code, the referring source location, the original reference, the resolved identity where one exists, the inclusion chain and a remedy where one can be stated accurately. A selected JSON format emits one object per line with no prose on that stream.

## Acceptance Criteria

- [ ] **AC1.** A candidate disagreeing with its recorded source provenance publishes nothing and fails, as the validation fixtures show.
- [ ] **AC2.** Untouched non-heading bytes and code examples in a published composite are identical to their sources, as the preservation fixtures show.
- [ ] **AC3.** A region boundary that would place content inside an unintended container fails with its declared error code, naming the source regions and the conflicting boundary, as the boundary fixtures show.
- [ ] **AC4.** A source whose content or canonical identity changes during compilation fails with a retry diagnostic and publishes nothing, as the consistency fixtures show.
- [ ] **AC5.** A source whose links carry composite destinations, recognized by a fragment whose first segment names a document path, is rejected, while one carrying such a fragment only inside code is composed, as the generated-input fixtures show.
- [ ] **AC6.** Each diagnostic carries a stable error code, the referring source location, the original reference, the resolved identity where one exists and the inclusion chain, as the diagnostic fixtures show.
- [ ] **AC7.** Selecting the JSON diagnostic format emits one JSON object per line on the diagnostic stream and no prose on that stream, as the JSON diagnostic fixtures show.
- [ ] **AC8.** A broken or self-referential link in an unselected section does not fail a composition that did not select it, as the validation-scope fixtures show.
- [ ] **AC9.** A file-wide parsing-safety limit exceeded by an unselected construct fails as an inability to index that source, as the file-wide safety fixtures show.

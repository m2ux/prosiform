## Overview

The repository's three trees, the README that explains what they are for, and the glossary that publishes the contract's vocabulary with the tool. Every later task of the initiative lands in the structure this task creates, and every later document draws its words from the glossary this task ships.

## Problem

The default branch holds a README and no other file, so the separation the plan assumes between the language-neutral corpus and the Python build exists only in a decision. The vocabulary the contract depends on lives only in the planning record, so a reader meets a closure, a region, a structural ancestor and a variant in the tool's diagnostics with no definition to hand, and a later author has nothing to keep the usage from drifting.

Nothing asserts any of this. A tree can be deleted, a README reference can rot against a moved planning file, and a term can enter the design without reaching the glossary, and each passes unnoticed.

## Proposal

The repository carries three trees, a README that is the way in, a glossary that ships with the tool, and three checks that hold all three true.

- **Three trees, each created by the stage that writes into it.**
  `fixtures/` holds the language-neutral corpus and the contract it encodes, `prototype/` holds the Python build, and `docs/` holds the documentation the repository owns. The production build's tree belongs to the initiative that writes that build, so nothing stands empty waiting for it. Each tree carries a short README naming what belongs in it.

- **The README states the tool, its installation and its invocation.**
  Purpose, repository layout, installation, invocation and the state of the work, with the design, the glossary and the plan reached by link. The design and the planning record stay on the engineering branch and are referenced rather than copied, so there is one copy of each.

- **The glossary is published with the build, not with the plan.**
  `docs/glossary.md` defines every term the contract uses, derived from the planning record's glossary and checked against the design and the epic criteria rather than copied wholesale. The design, the criteria, the corpus and the tool's diagnostics draw their vocabulary from it.

- **Three checks, each failing on the condition its criterion forbids.**
  A layout check reads the three trees from the index and fails when one holds no tracked file. A link check resolves every reference the README carries and fails on one that does not resolve. A vocabulary check takes the contract's term inventory from the planning record's glossary, finds the terms the design and the epic criteria use, and fails on one the shipped glossary does not define. Each is a standalone script under `checks/`, run directly and returning a nonzero status on failure; W03 brings them under one documented command.

| Analysis | The trees this stage needs, what belongs in each, the contract terms the design and the epic criteria use, and the reference classes the README carries |

| Review | Confirmed that no design or planning content is copied rather than linked, that no tree is created for a build this stage does not write, and that each glossary entry the shipped file adds is a term the design uses |

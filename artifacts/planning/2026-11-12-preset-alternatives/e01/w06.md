## Overview

A live run of the agent-pick workflow measures how often an agent resolves a `?` pick from what the bundle and `pf` print, and commits the result as the workflow's own run record beside the baseline.

## Problem

- **The workflow has no measurement.**
  A designed workflow proves the scenarios are well formed; only a live run shows whether agents pick correctly.
- **The runbook has no agent-pick run.**
  `RUNBOOK.md` gives each live run its own section, and none states this one's model, caps or record.

## Proposal

**The scene.** `RUNBOOK.md` sets how a live run is planned, run, reviewed and recorded. Agent-pick is an edge workflow, so its record sits in its own files and `baseline.json` is untouched.

- **The runbook section.**
  An Agent-Pick Run section on the baseline's harness and model as the user named them, `--workflows agent-pick --forms compiled`, five repetitions, its caps set by its shakedown, and its committed files.
- **The shakedown.**
  One repetition of each scenario; its largest session and mean cost set the run's session cap, token budget and cost cap by the proof's rule.
- **The run.**
  `make eval-diagrams` live with those arguments once the user approves the cost cap.
- **The record.**
  The run's `report.json` as `agent-pick.json` and its `report.md` as `agent-pick.md`, each failing session with the rubric's disposition, and the run's measured cost in the README.

## Work Breakdown

| Part | Description |
| --- | --- |
| Analysis | The edge run's section as the pattern for this one |
| Plan | The runbook section, confirmed by the user |

| Review | Give each failing session the rubric's disposition before committing |
| Test | `make eval-harness`, `make check` and the committed record |

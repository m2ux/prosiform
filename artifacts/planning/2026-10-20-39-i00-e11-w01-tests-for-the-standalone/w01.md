**Component:** `checks/tests`

## Overview

This task puts the repository's five standalone checks under tests that run beside the corpus harness, and holds the link check's heading-slug rule to the anchors GitHub generates for the same headings. The checks are what the repository trusts to read its own documents, and until now the only one with tests of its own was the link check's reachability verdict.

## Problem

The standalone checks parse documents, a `Makefile` and a project definition, and nothing observes that parsing.

- **The slug rule agrees with GitHub by observation rather than by command.**
  Twelve README headings were measured against GitHub's rendered anchors once, at one revision, and recorded in a planning folder. No test re-runs the comparison, so a later edit to the rule is caught by review or not at all.

- **A parser that misreads a document reports a clean run.**
  The table reader, the term inventory, the tree listing and the reference reader each turn text into the set a check compares, and a parser that drops a row, keeps a fenced example or splits a cell wrongly narrows what the check looks at without failing.

## Proposal

The checks' commands run over the repository's own documents, where every parse happens to be correct, so a parse that is wrong in general passes every day. The tests give each parser input of its own, written to be the input it reads wrongly, and the slug rule a comparison whose answer comes from GitHub.

- **GitHub answers for the slug rule, and its answer is recorded.**
  A document of nineteen headings is rendered by GitHub's Markdown API and the anchor ids it generates are captured beside the bytes it was given. The test feeds those same bytes to the link check's fragment reader and holds the fragments it produces to the ids GitHub generated. The capture is committed, so the comparison is a command the suite runs rather than an observation in a record, and refreshing it is one documented call.

- **The oracle carries the headings a rule gets wrong.**
  Emoji and variation selectors, accents, a code span, a link, emphasis, an ampersand between two spaces, an intra-word underscore, a trailing run of hash marks and a repeated heading are all present, because a rule written in terms of word characters, or of the characters rather than the classes that survive, parts company with GitHub on one of them.

- **Each standalone check gets a test module naming it.**
  `test_slug.py` holds the slug rule to the capture, `test_links.py` gains the reference and fragment reading beside its reachability cases, and `test_layout.py`, `test_tables.py`, `test_vocabulary.py` and `test_smoke.py` hold the tree listing, the command and declaration tables, the term inventory and the installed command's responses. Each module gives its parser a document, a `Makefile` or a help response the parser would read wrongly, so the test fails when the parsing drifts rather than when the repository changes.

- **The rule is corrected where GitHub disagrees with it.**
  Underscore emphasis is consumed by GitHub's rendering and the rule keeps it, so `_underlined_` yields an anchor with underscores GitHub does not generate, while `snake_case` keeps the one it does. The rule reduces emphasis to its text as it already reduces a code span and a link, which is what the capture requires to pass.

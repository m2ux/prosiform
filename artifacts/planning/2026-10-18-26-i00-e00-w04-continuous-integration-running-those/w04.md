## Overview

Continuous integration running the same commands a developer runs. A job on every change to the branches that carry the build installs the environment from the lockfile, runs the documented check commands, and fails the change when one of them fails. It covers AC4, the last unticked criterion of this epic.

## Problem

A check that exists only locally passes silently when it is skipped, and one that exists only remotely cannot be reproduced before a change is pushed. The eight named commands hold the repository's claims true only where someone remembers to type them.

## Proposal

The checks are already one set under one name: `make check` runs the eight targets in the order the Makefile declares, stops at the first failure, and prints the target that failed. Continuous integration calls that name rather than listing the targets again, so the set a change is gated on is the set the Makefile defines, and a target added to it is enforced remotely the day it is added. A reviewer reads one configuration, and the Actions log names the failing check in Make's own output.

The job carries four things the checks need:

- **The toolchain the lockfile pins.** The job installs `uv` at the version the records document and runs `make check`, whose first four targets call `uv run --frozen`: the lockfile decides every Python version and tool version the run uses, and the job decides none of them.
- **A credential that reaches the tracker.** The link check reads four issues and the project board through the GitHub API, because a private repository answers an unauthenticated request with 404. A user-owned project sits outside the repository scope the built-in token is confined to, so the job exports the `PROJECT_READ_TOKEN` secret as `GH_TOKEN`, which is the variable `gh` reads.
- **The branch history the checks resolve through git.** The link check resolves a blob or tree URL into another branch of this repository with `git rev-parse`, `git cat-file` and `git show`, and the vocabulary check reads the design and the epic criteria from the branch the README's Design link names. The checkout takes `fetch-depth: 0`, so every branch is present whichever one the README names; naming a branch in the job instead would put a second copy of that decision beside the README's link, where it would rot silently.
- **A trigger on the branches that carry the build.** The job runs on a push to `main` and to the initiative namespace `i[0-9][0-9]/**`, which is where the build and the branches targeting it live. One event means one run for a change, rather than a push run and a pull-request run for each. The `workspace` and `engineering` branches carry the tooling and the planning records and hold no build to check.

The slug a heading yields is the one GitHub generates. It holds the heading's letters, numbers and combining marks, its hyphens and its underscores, drops its punctuation and symbols, and turns each remaining space into a hyphen, trimming nothing. A heading opening with an emoji therefore yields a leading hyphen, so a fragment link that resolves in the check resolves on the page.

## Work Breakdown

| Part | Description |
| --- | --- |
| Analysis | The job environment, the version of `uv` it installs and what the lockfile decides for it; the credential the link check needs and the scopes it was issued with; the branch history the link and vocabulary checks resolve through git; the anchors GitHub generates for the README's own headings |
| Plan | One step calling `make check` rather than one step per target, so the gated set is the Makefile's; the push trigger and the branches it names; `fetch-depth: 0` rather than a named fetch; the secret exported as `GH_TOKEN` on the step that runs the checks |
| Implementation | The workflow, its checkout, its `uv` installation and its one check step; the link check's slug rule brought to the one GitHub generates |
| Review | Confirmed that the job runs the documented commands rather than its own variants, and that no secret value is printed by a step or a check |
| Test | A deliberate violation of each of the eight checks fails the job and the clean tree passes it, as the Actions runs show; the slug rule generates, for every heading of the README, the anchor GitHub's own rendering of that README carries |

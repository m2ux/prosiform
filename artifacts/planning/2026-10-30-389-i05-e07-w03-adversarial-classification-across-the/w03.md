**Component:** evals/diagram-following/test_run.py

## Overview

Four dispatch scenarios, each written in a compiled and an authored form, driven by every departure the stub agent can state, so each of the eight-scenario corpus's cells is classified by the class that departure predicts. The scorer's discrimination is then held across the corpus rather than by one hand-written case per check.

## Problem

The dispatch checks are tested one departure each on one scenario: `undispatched` on `dispatch-chain`, `sequential_set` on `dispatch-set`, `unrelayed_question` on `dispatch-question`. A check that only ever meets the departure it was written for is not shown to tell one departure from another. A class that fired for the wrong reason — `sequential_set` reported for a question answered in the sub-agent's place, say — passes every test the corpus holds, because no test puts a scenario beside a departure other than its own.

The dispatch corpus's two forms double that gap: nothing runs a departure over both, so a form-specific misfire in the transcript reader would pass as well.

## Proposal

- **The corpus is the matrix.** Four scenarios across two forms is eight cells per departure. Each departing script runs the whole corpus once, so every scenario meets every departure it can fail.
- **Each cell states its class.** A script states one departure; a scenario's trace states whether that departure changes anything about it. Where it does, the cell reads that class and no other; where it does not, the cell passes. A class firing where its departure is absent fails the same assertion.
- **One clean run.** With no script set, every cell passes, so the matrix is not a list of ways to fail a scorer that would pass anything.
- **A fixture run, not a measurement.** The stub walks the workflow's own diagram, so its pass rates are correct by construction. No baseline is written and no paid session starts.

## Work Breakdown

| Part | Description |
| --- | --- |
| Analysis | Which departure each script states; which of the four scenarios each departure can change; and the class each affected cell must therefore read. |
| Plan | The matrix: four scripts, each over four scenarios in two forms, with a cell per scenario and form; plus the clean run. |
| Implementation | `dispatch_run()` runs the corpus once; `test_a_departure_is_classified_across_every_dispatch_scenario` parametrised by script asserts each cell's class; `test_a_clean_run_passes_every_dispatch_cell` asserts every cell passes; `test_the_departure_table_names_every_dispatch_scenario` holds the table to the corpus. |
| Review | Each script's predicted class is the class the runner records, and the run's cell count is the corpus's; a departure that changes nothing for a scenario reads a pass rather than a class. |
| Test | AC4: the four parametrised matrix tests, the clean run, and the table check, run by `make check` against the stub agent with no paid session and no baseline written. |

### Test

AC4 is one duty — every dispatch scenario in each form classified by the class its departing stub agent states — so the Test part names the matrix, its clean counterpart, and the check that the matrix is the corpus's.

| Reading | Test |
| --- | --- |
| Each script over every scenario in both forms takes the class it predicts, and passes where its departure changes nothing. | `test_a_departure_is_classified_across_every_dispatch_scenario[STUB_AGENT_NO_DISPATCH]`, `[STUB_AGENT_SEQUENTIAL]`, `[STUB_AGENT_ANSWER]`, `[STUB_AGENT_STOP]` |
| With no script set, every scenario in both forms passes. | `test_a_clean_run_passes_every_dispatch_cell` |
| The matrix's cells are the corpus's, one per scenario per form, so no scenario is silently absent from a departure's run. | `test_the_departure_table_names_every_dispatch_scenario`, and the cell-set assertion in each matrix test |

## Boundaries

The run is a fixture run. `STUB_AGENT_STOP` is a walk that stops short, so its class is `unfinished` — the completion check read before any dispatch check — which is the corpus's statement that the ordering holds across scenarios, not a dispatch class of its own. A scenario the departure leaves as the scenario states predicts a pass, so the table records the absence of a class as plainly as its presence.

No baseline is written: `baseline.json`, `report.md` and `EVAL_BUDGET_USD` are untouched, and the measured baseline belongs to I05:E08 W02.

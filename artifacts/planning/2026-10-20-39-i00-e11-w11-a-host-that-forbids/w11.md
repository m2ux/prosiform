## Overview

The verdict a host answering 403 to both methods takes, decided and stated.

## Problem

The link check tells a reference that does not resolve from a host that did not answer, and the boundary sits at 500. A forbidden response falls on the failing side, and it is not obvious that it belongs there.

- **Forbidden is not absent.**
  The status says the caller may not have the resource, not that the resource is not there.

- **Neither reading is free.**
  Counting it as silence publishes a reference nobody can follow as resolved. Holding the document to it reddens a run for a correct reference whenever a host declines to serve a checker.

## Proposal

A forbidden response is counted as unreachable: three bounded attempts, a warning line, a passing run. The `HEAD` 403 then `GET` re-ask is unchanged, so a host refusing only the method still resolves.

The decision rests on where the refusal is decided. A 403 that survives a browser user agent is a decision about the requesting network rather than about the agent or the target, so the same address serves the reader who follows the link and refuses the run that checks it. A status recording where the check ran states nothing about the document.

The counter-cost is smaller than it reads. An unreachable address is named on a warning line on every run, so a reference genuinely forbidden to everyone is reported rather than silenced.

A status of 401 and a method refusal of 405 keep the failing verdict, deliberately and in writing: an authorization scheme is one a caller could satisfy. The evidence for those is [#98](https://github.com/m2ux/prosiform/issues/98).

**Component:** `checks/independence.py` — the independence check.

## Overview

The check that the corpus and its conformance report bind behaviour rather than an implementation: every declaration a fixture carries and every entry the report prints is scanned for an implementation language, a module path, a source-file path, an internal identifier or internal error wording, and a hit fails the check naming where it was found and the term it is.

## Problem

A fixture naming a module, a flag spelling or an error-message wording specific to one implementation binds that implementation rather than the contract. The corpus is the artifact a second implementation is held to, so such a reference reads as a requirement and is met by copying the first build rather than by meeting the design.

Nothing holds it out today. The manifest schema states that nothing in a manifest names an implementation, a module or a language, and the runner reaches the build under test through configuration so that it names none itself, but both are statements about the shape of a declaration rather than about the words inside one. A `description`, a `clauses` entry, a `message_contains` substring and a clause name the design states are all free text, and free text is where an implementation term arrives.

## Proposal

- **The scan reads declarations and report entries, not the documents under test.**
  A fixture's manifest states what the fixture establishes about the contract, so it is a claim and is held to this rule. A fixture's source tree and its expected standard output are the document the run consumes and the bytes it must reproduce: they are input and output of the behaviour rather than statements about it, and the corpus deliberately bundles real documents that name real source files. The scanned text is therefore every string a manifest declares, the fixture identities those manifests belong to, and the rendered conformance report, which carries the design's clause names, the declared surface and those same identities.

- **The inventory is three kinds of term.**
  An implementation language or runtime; module and packaging machinery, a source-file path among it; and the wording a build's own fault reporting uses in place of the contract's codes. Each is matched whole-word and without regard to case, and a term's entry says what it names, so a hit is read as the reason it is refused rather than as a string that matched.

- **A hit names where it was found and what it is.**
  A failure gives the fixture's identity or the report section, the term, and what that term names, so the fixture is found and the fix is apparent.

- **The contract's declared names are held apart from the inventory rather than excluded from the scan.**
  The error codes, the warning codes and the exit statuses the schema declares and the options the documented invocation names are interface terms. Rather than subtracting them from each scanned text, the check scans those declared names themselves: a declared name matching the inventory is a reported failure, which leaves the inventory and the contract's surface provably disjoint and makes the scan need no exclusion of its own. A contract that came to declare an implementation term is then the failure it is, rather than a term quietly admitted.

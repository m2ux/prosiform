## Overview

A run states that its sessions carried a managed configuration, how much of it, and a fingerprint that tells two configurations apart, and names nothing in it, so no platform's configuration is written into the repository.

## Problem

- **A run record names the managed configuration.**
  `run.json` and the report name each managed plugin with its version and each environment key the signed remote settings add, so every committed record carries one platform's configuration.
- **The documents describe one configuration.**
  The eval's README and `RUNBOOK.md` describe what a particular managed plugin's hook does, and the tests reuse its version and keys.

## Proposal

**The scene.** The Claude harness's preflight accepts a plugin installed or enabled at managed scope and a hook in the host's managed settings, and the run records them.

**The design.**

- **Counted, not named.** (User, 2026-11-03.)
  The run record and the report state how many managed plugins, managed environment settings and managed hooks the sessions carried, and a fingerprint of that configuration: a hash over the plugin identifiers and versions, the environment keys and the hook events, so two runs on one configuration show the same fingerprint. Nothing in it is named.
- **Generic documents.**
  The README and `RUNBOOK.md` state that a managed configuration may reach every session and that the run counts and fingerprints it; they describe no particular plugin, hook or setting. Test fixtures use neutral placeholder identifiers.
- **One shape for every managed scope.**
  I10:E02 W02 records the host's managed settings hooks on `i10/e02/main`; whichever of E02 and E05 reaches `main` second folds its hooks into the same counted, fingerprinted record.

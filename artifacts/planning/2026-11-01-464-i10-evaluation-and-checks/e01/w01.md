**Component:** .github/workflows/checks.yml

## Overview

The checks workflow decides whether to run from the branch name alone. This task makes it run on every pull request whose change touches the build, the corpus or the checks, whatever its branch is called, and on every push to `main`.

## Problem

- **The trigger reads a branch name.**
  The workflow runs on a push to `main` or to a branch matching `i[0-9][0-9]/**`, and on nothing else.
- **The name misses build changes.**
  Over the eleven most recent merged pull requests, three changing 29, 9 and 27 files under `src/`, `fixtures/` or `checks/` ran no workflow, and four changing no build file ran one.
- **A branch cut from `engineering` holds no workflow file.**
  The planning branch carries no build, so a branch descended from it cannot run the checks whatever it is called.

## Proposal

**The scene.** The workflow holds one job that calls `make check`. A pull request into a branch that carries the build is where a change is accepted, so that is where the checks decide whether to run.

- **The trigger is the pull request and the push to `main`.**
  A pull request into a branch carrying the build runs the workflow, and so does a push to `main`.
- **The changed paths decide whether the checks run.**
  A change touching the build, the corpus, the checks, the documentation the checks read or the workflow itself runs `make check`; the set of paths is stated once, in the workflow.
- **The branch name decides nothing.**
  The initiative naming pattern leaves the trigger, so a branch is checked for what it changes.

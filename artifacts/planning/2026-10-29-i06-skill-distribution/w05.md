**Component:** fixtures/usage-example (the branch's fixture corpus)

## Overview

Each usage-example fixture reaches the skill from the corpus it sits in, and its expected bundles record what the branch's tree produces.

## Problem

A fixture's `source` link resolves `../../../example/work-planner`, a path that names a directory in another repository. Checked out on its own, the branch's fixtures resolve to nothing, and a copied tree would let the fixture and the published invocation drift apart.

## Proposal

- **The link points inside the corpus.**
  `source -> ../../work-planner`, so the fixture names the tree beside it and the corpus keeps one tree.
- **The expected bundles are regenerated once.**
  The bundles a fixture records are those its invocation produces from the branch's tree, so a re-rooted fixture does not keep a bundle from the old one.
- **The manifest's description is the branch's.**
  A description that narrates a dispatched set or a grouping states what the branch's tree does.

## Work Breakdown

| Part | Description |
| --- | --- |
| Analysis | Each fixture's current `source` target, and which expected bundles change with the tree. |
| Plan | The new link target and the fixtures whose expected bundles are regenerated. |
| Implementation | The links repointed and the expected bundles regenerated from a configured build. |
| Review | Each fixture's description against the bundle it now expects. |
| Test | The corpus run meeting every manifest on the branch. |

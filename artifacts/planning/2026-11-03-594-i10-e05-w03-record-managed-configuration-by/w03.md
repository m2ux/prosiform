## Overview

A run states that its sessions carried a managed configuration, how much of it, and a fingerprint that tells two configurations apart, and names nothing in it, so no platform's configuration is written into the repository.

## Problem

- **A run record names the managed configuration.**
  `run.json` and the report name each managed plugin with its version and each environment key the signed remote settings add, so every committed record carries one platform's configuration.
- **The documents describe one configuration.**
  The eval's README and `RUNBOOK.md` describe what a particular managed plugin's hook does, and the tests reuse its version and keys.

## Proposal

**The scene.** The Claude harness's preflight accepts a plugin installed at managed scope or enabled by the signed remote settings, and `Claude.managed()` returns each such plugin with its version and the environment keys those settings add; `run()` writes that under `managed` in `run.json`, and `report.py` names each item on the report's managed line.

**The design.**

- **Counted, not named.** (User, 2026-11-03.)
  `managed` in `run.json` holds four values: `plugins`, `environment` and `hooks`, each a count, and `fingerprint`. Nothing in it is named.
- **The configuration the counts read.**
  A managed plugin is one installed at managed scope or enabled by the signed remote settings. A managed environment setting is a key those signed settings' `env` adds. A managed hook is an event a managed plugin's `hooks/hooks.json`, under its install path, declares a hook for.
- **The fingerprint.**
  A SHA-256 hex digest over the canonical JSON of the sorted plugin identifiers with their versions, the sorted environment keys and the sorted hook events, so two runs on one configuration give one fingerprint and a changed version, key or event gives another. A run with no managed configuration records null.
- **One function for every harness.**
  A module-level function in `harness.py` turns the identifiers into the counted record, so the Claude harness and the two harnesses that read no managed configuration return one shape.
- **Hook responses.**
  A hook's response is accounted for where the run counts a managed plugin or a managed hook.
- **The report.**
  The report states the three counts and the fingerprint, or that the sessions carried no managed configuration.
- **Generic documents.**
  The README and `RUNBOOK.md` state that a managed configuration may reach every session and that the run counts and fingerprints it; they describe no particular plugin, hook or setting. Test fixtures use neutral placeholders such as `plugin-a@example` 1.0.0 and `EXAMPLE_SETTING`.
- **One shape for every managed scope.**
  I10:E02 W02 records the host's managed settings hooks on `i10/e02/main`; whichever of E02 and E05 reaches `main` second folds those hooks into the same counted, fingerprinted record.

## Validation

Tested at revision `c368152c` of `i10/e05/w03-record-managed-configuration-by`. Every test plants its configuration directory under a temporary path; no test reads a real configuration and no paid session ran.

### T1 Managed configuration recorded by count and fingerprint

`test_a_managed_configuration_is_recorded_by_count_and_fingerprint` in `test_run.py` installs a placeholder plugin at managed scope with a hooks file declaring one event, and signed remote settings enabling it with two environment keys. The stub agent's session starts and writes a hook response, which the run accounts for. `run.json` records `managed` as one plugin, two environment settings, one hook and a 64-character hex fingerprint; the report shows that fingerprint; and neither file names the plugin, its version, a key or the event. Observes AC9.

### T2 Fingerprint tells two configurations apart

`test_a_fingerprint_tells_two_managed_configurations_apart` in `test_run.py` reads the Claude harness's managed record for six configuration directories. Two identical configurations give one fingerprint; a changed version, environment key or hook event each gives a distinct one, though the counts are equal; a directory with nothing managed gives zero counts and a null fingerprint. Observes AC9.

### T3 Report states counts and fingerprint, naming nothing

`test_the_report_counts_the_managed_configuration_every_session_carried` in `test_report.py` reads a run record holding counts and a fingerprint. `report.json` carries the record as written, `report.md` states the three counts and the fingerprint, and a record with nothing managed reads `none`. Observes AC9.

### T4 Search of the tree

Fixtures use neutral placeholders: `plugin-a@example`, `plugin-b@example`, `1.0.0` and `EXAMPLE_SETTING`. Observes AC9.

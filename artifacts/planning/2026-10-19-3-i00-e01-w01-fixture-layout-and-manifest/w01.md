## Overview

The shape a fixture takes on disk, the manifest schema that declares one, the catalogue of error codes a fixture may expect, and the validation that rejects a manifest the schema does not describe.

## Problem

The behavioural contract is prose. A clause of it has no executable form, and nothing states what a case of it consists of, so there is no artifact a second implementation can be held to.

`fixtures/` holds a README and no fixture. Nothing says where a fixture's source tree sits, where its expected output sits, or what a manifest contains. A corpus written without that settled gains a different declaration per author, and the first one a runner cannot read is the one that fixes the format by accident.

The error codes have no owner. The design names twelve of them across its failure clauses, and every epic downstream says the tool fails "with its declared error code" while nothing declares the set. A fixture expecting a failure can therefore name a code the tool will never emit, and the corpus records the mistake as the contract.

## Proposal

A fixture is a directory holding one manifest, the source tree it bundles and the bytes it expects back. The manifest is the whole declaration: a runner decides pass or fail from it and the fixture's files alone, and nothing in it names an implementation, a module or a language.

- **A fixture is a directory carrying `manifest.toml`.**
  Discovery walks `fixtures/` and takes every directory holding that file, so a fixture's identity is its path under `fixtures/` and the corpus groups into families by directory without the rule changing. A fixture holds `source/`, the tree the run is confined to, and `expected/`, the bytes it must produce. Keeping the two apart means no expected bundle is ever read as a source, which matters because an expected bundle is itself Markdown and the generated-input policy refuses one as input.

- **The manifest is TOML.**
  TOML has one specification at version 1.0.0, a reader in the Python standard library as `tomllib`, and the canonical Rust crate the production build will already carry. Its scalars are typed, so an exit status is the integer `1` rather than the string `"1"` and a schema can say so. JSON would carry an expected bundle only as an escaped blob, and YAML has no standard-library reader here, several dialects, and whitespace rules that fight Markdown content.

- **Expected output is a sibling file the manifest names.**
  `expected.stdout` is a fixture-relative path, and `expected/stdout.md` holds the bundle byte for byte. Bytes belong in a file: the preservation invariant turns on newline spelling and a trailing newline, which a TOML multi-line string does not carry across parsers intact, and the corpus already needs CRLF fixtures. A bundle in a file is also reviewable and diffable as the Markdown it is. The declaration still sits in one manifest, which is what the criterion asks: the manifest names every expectation, and one of them is named by path. A fixture expecting no bundle carries an empty `expected/stdout.md`, so "nothing on standard output" is stated rather than left to an absent field.

- **The schema is a JSON Schema document in the corpus.**
  `fixtures/manifest.schema.json` is a JSON Schema 2020-12 document, and it is the artifact both builds honour. A schema written as Python would have to be read and reimplemented by the Rust runner, which is the failure mode the whole epic exists to avoid; a published schema language has a validator in both ecosystems and makes the schema data rather than code. TOML's value model is a subset of JSON's, so a parsed manifest validates directly with no intermediate form.

- **The catalogue is an enumeration inside that schema.**
  `expected.diagnostics[].code` takes its value from a twelve-member `enum`, one member per error code the design names. A manifest naming anything else fails validation before it reaches a runner, so a fixture cannot expect a failure the contract does not define.

- **Validation is one named command, `make corpus`.**
  The command runs the corpus's own test suite under `checks/tests`: the schema tests that observe the criteria, and a test that validates every manifest the corpus holds. It is separate from `make test`, which is the Python build's suite, because the corpus is not the build and its checks must outlive it — the Rust initiative runs the same corpus and does not run `prototype/tests`. `make check` runs it with the rest.

- **`checks/manifests.py` holds the reader and the validator.**
  It loads the schema, reads a manifest, and returns the validation errors for one. The corpus runner W02 builds reads its validation from this module rather than repeating it, so a manifest is checked the same way wherever it is read.

- **The catalogue is held to the design mechanically.**
  A test reads the design from the branch and path the README's Design link names, as the vocabulary check already does, collects every `E_`-prefixed code it carries, and requires the schema's enumeration to be exactly that set. A thirteenth code in the design fails the check until the schema carries it, so the catalogue cannot drift away from the contract it was derived from.

### The Catalogue and Where Each Code Comes From

Each code is the design's own; none is invented here.

| Code | Design clause |
| --- | --- |
| `E_AMBIGUOUS_FILE_GROUP` | File-scoped hierarchy — two documents whose paths differ only by Markdown extension |
| `E_AMBIGUOUS_SOURCE_HEADING` | Source-heading resolution — two headings in one source producing one slug |
| `E_GENERATED_INPUT` | Generated input policy — a source opening on a file heading |
| `E_HEADING_DEPTH_OVERFLOW` | File-scoped hierarchy, Depth overflow — an emitted heading beyond H6 |
| `E_INVALID_GROUP_RULE` | Grouping — a rule's depth outside 1 through 6, an unknown slug, or a repeated slug |
| `E_NESTED_SECTION_TARGET` | Section extraction and output hierarchy, Nested target — a fragment naming a container-nested heading |
| `E_PARSER_REFERENCE_LIMIT` | Mandatory parser viability gates, Observable reference-resolution suppression |
| `E_SOURCE_OUTSIDE_ROOT` | Reference normalization and path identity — a normalized path outside the allowed root |
| `E_SOURCE_SYMLINK` | No-symlink source policy — a source path containing a symlink below the root |
| `E_TARGET_NOT_FOUND` | Validation and failure contract — a local Markdown reference that resolves to no document or section |
| `E_UNSAFE_BUNDLE_BOUNDARY` | Block boundaries — a boundary merging content into an unintended container |
| `E_UNTERMINATED_FRONTMATTER` | Frontmatter policy — a recognized opener with no closing delimiter |

The design names these twelve and no others, which is the count the planning decision records. Every code it names carries the `E_` prefix and describes a failure; the design describes two warnings — a grouping rule that arranges nothing, and resource portability — and names a code for neither, so the catalogue is closed over errors alone and a warning diagnostic cannot yet be declared in a fixture.

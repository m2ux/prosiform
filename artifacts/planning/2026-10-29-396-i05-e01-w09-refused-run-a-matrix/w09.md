**Component:** evals/diagram-following/run.py

## Overview

A run whose every session errors is currently recorded as a completed run: `run.json` says 200 started, zero cost, nothing skipped, and a report compares pass rates against a baseline. This task records such a run as refused, quoting the agent's own words as the reason, so a spent login is never read as a matrix of failing agents.

## Problem

- **A refused run is recorded as a completed one.**
  Run `20261029T143428Z` started all 200 sessions and every one was refused by the login's weekly limit. `run.json` records 200 started, `cost_usd` 0.0 and an empty `not_started`, and a report was written and compared against the baseline.
- **The agent's words are discarded.**
  Each session's `result` message carries the refusal, and one refused session says the login is spent, but nothing reads them together to decide the run's state.
- **A report over a refused run reads as a result.**
  Its tables give pass rates and changes against a baseline for a run in which no agent entered a state.

## Proposal

The runner finishes its sessions, then decides the run's state before it writes `run.json`.

- **A run refuses a matrix it cannot complete.**
  A run that started every session of its matrix and every one of which took the `errored` verdict is recorded as refused: `run.json` carries `"state": "refused"` and a `reason`, and the report names both instead of comparing pass rates.
- **The reason is the agent's own.**
  One session's `result` text is quoted as the reason, so a reader sees the limit the login reported rather than a count of errors. A session that printed no text records that rather than an empty string.
- **The boundary is a started and wholly errored matrix.**
  The decision sits in `outcome`, called once the pool has settled. A run its budget stopped part way started less than its matrix, so it is a completed run with sessions not started; one where some sessions errored on a genuine fault beside sessions that entered a state is a completed run whose failures are its result. Both are reported as results.
- **The report reads the state rather than inferring it.**
  `report()` takes `state` and `reason` from `run.json`, gives no row at any level and no baseline comparison when it is refused, and prints the state, the reason and a statement that nothing was compared. `--write-baseline` refuses a refused run, which has no cells to write.
- **The state is held by a test.**
  A stub-agent test drives a run in which every session errors, asserting the refused state in `run.json` and the report, the quoted reason, and the withheld rows and comparison. A second test drives a genuine mix, and a third a budget-stopped run, so the boundary is observed in both directions.

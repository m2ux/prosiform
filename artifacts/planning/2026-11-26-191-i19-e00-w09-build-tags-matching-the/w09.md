## Overview

A repository check reads the release tags naming the commit under test and fails when they assert something the build does not report. A release's build tag, its contract tag and the version `pf -v` reports are set in three places, and nothing holds them to each other.

## Problem

- **A build tag can name a commit that reports another version.**
  Tagging the wrong commit, or declaring a new version after tagging, leaves `python/vX.Y.Z` on a build whose `-v` answers with another number. No check reads a tag, so `make check` stays green over it.

- **A build tag and a contract tag can disagree.**
  The versioning policy holds a build's major and minor to the contract revision it implements. A release commit carrying `python/v0.36.0` beside `contract/v0.35.0` asserts two contract revisions at once, and nothing reports it.

## Proposal

A release is one merge on `main` carrying `contract/vX.Y.Z` and `python/vX.Y.Z`, and step 5 of [Cutting a release](https://github.com/m2ux/prosiform/blob/main/docs/versioning.md#cutting-a-release) creates both tags by hand.

- **`make tags` reads the tags naming HEAD.**
  `git tag --points-at HEAD` lists every tag naming the commit under test, an annotated tag by the commit it names. Tags under `python/` and `contract/` are release tags; every other prefix in the repository (`workflows/`, `workspace/`) names something else and is passed over.

- **A build tag is held to the build's own report.**
  The version is read from the build under test's `-v`, the line `pf 0.35.0 (prosiform-markdown)` whose word before the profile is the version, because the tag asserts what the build reports. The build is the one `PROSIFORM_BUILD` names, as for the corpus, through `invocation.py`'s reading of the build's output.

- **A contract tag beside a build tag shares its major and minor.**
  A contract tag alone names a contract revision tagged in its own right and passes.

- **A release tag not spelled `vX.Y.Z` fails.**
  `python/v0.36` names no version the build can report.

- **A commit carrying no release tag passes without running the build.**
  Every pull request and every push to `main` is such a commit, so the check constrains releases alone.

- **Where it observes a release.**
  The tags are pushed after the release merge's own run, and the workflow is not triggered by a tag push, so continuous integration never runs on a tagged HEAD unprompted. `actions/checkout` with `fetch-depth: 0` fetches every tag, so a manual dispatch of the `Checks` workflow on the tag reads them. The release procedure runs `make tags` locally once both tags are made and before they are pushed, since a pushed tag never moves.

## Overview

The Python build's project definition, the lockfile that pins what a checkout installs, and the command that creates an environment from it. The definition also carries the shipped glossary into the installed package.

## Problem

The parser the prototype is to be written against is decided and unpinned, so two checkouts can resolve different parser versions and disagree about what a document means. A fixture corpus whose expected bundles rest on that disagreement binds nothing, and a divergence between the two builds could not be read as a defect in either.

The glossary reaches only the source tree. The epic requires it published with the build, and until a project definition exists there is no distribution to assert that against.

## Proposal

The Python build lives in `prototype/`, and its project definition sits at the root of that tree, which is where the README's install command points. The definition declares the supported Python version and the build's dependencies; a lockfile beside it records the exact version and hash each dependency resolves to; and a documented command creates an environment from that lockfile without resolving anything.

- **The declared profile decides the dependency set.** `skill-markdown-v1` needs pipe tables, double-tilde strikethrough, source task-list markers preserved without checkbox HTML, typographic substitution disabled, and raw HTML recognized so it can be refused. `markdown-it-py` supplies all five: the first two as core rules its CommonMark preset enables on request, the third by leaving the plugin that renders checkboxes out, the fourth by leaving its typographer off, and the fifth as a token of its own. No parser plugin package is required, so none is declared; `mdurl` arrives as the parser's own dependency and is recorded in the lockfile rather than declared.

- **The pin is exact, in both places that hold one.** The project definition pins the parser to one version rather than a range, so an installer that reads no lockfile still obtains that version. The lockfile records the resolved version and its artifact hash, so an installer that reads it obtains those bytes.

- **The environment command resolves nothing.** `uv sync --frozen` installs what the lockfile records and fails rather than re-resolving, so a dependency reaches an environment only by way of a lockfile change. `uv sync --check` reports an environment whose installed versions have drifted from the lockfile, which is the instrument the criterion's negative case needs.

- **The wheel carries the glossary.** The documentation tree is the glossary's one home, and the build target force-includes `docs/glossary.md` into the package at `prosiform/docs/glossary.md`. An installed build then holds the vocabulary its diagnostics draw on, and the source tree still holds one copy.

- **The package is the smallest thing that installs.** The build implements no behaviour yet, so the package is a module that names what it will be and the package data it ships. The parser's configuration against the profile belongs to the epic that writes the build.

## Overview

The Layered Calls pattern page: a layered architecture, where every call goes down the stack and high-level modules depend in the direction of abstraction, realised by `group` pairs, merged groups and placement order, with a specimen the build compiles and checks.

## Problem

- **The grammar affords it, and nothing names it.**
  `group` pairs, merged groups and placement order already behave as a layered architecture, but no page tells an author so.
- **An author re-derives it per skill.**
  Without a named pattern, each skill states its own version of the structure as private rules.

## Proposal

**The scene.** The catalogue's template and checks are in place, and the Shared Rule page shows a conforming page and specimen.

**The design.**

- **Paradigm.**
  A layered architecture, where every call goes down the stack and high-level modules depend in the direction of abstraction, cited from Martin, Solid Relevance (dependency inversion).
- **Grammar.**
  `group` pairs, merged groups and placement order, each linked to its documentation section.
- **Specimen.**
  A tree at `docs/patterns/layered-calls/`: a mode calling a protocol that calls two artifact operations, each layer's documents declaring that layer's group.
- **What the bundle shows.**
  One division per layer, standing in layer order: modes, protocols, artifacts, committed as the specimen's expected bundle set.
- **Principles.**
  The page's `Related` names the SOLID principles it serves: dependency inversion, single responsibility.
- **The limit to probe.**
  The page states whether a link up the stack, from an artifact to a mode, can be refused; a limit found is stated under `Limits` and raised as its own issue.

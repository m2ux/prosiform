## Overview

The Staged Compilation pattern page: multi-stage programming and partial evaluation: a program specialised on what is known now, leaving a residue for later, realised by deferral, and a deferred composition activated by a later run, with a specimen the build compiles and checks.

## Problem

- **The grammar affords it, and nothing names it.**
  Deferral, and a deferred composition activated by a later run already behave as multi-stage programming and partial evaluation, but no page tells an author so.
- **An author re-derives it per skill.**
  Without a named pattern, each skill states its own version of the structure as private rules.

## Proposal

**The scene.** The catalogue's template and checks are in place, and the Shared Rule page shows a conforming page and specimen.

**The design.**

- **Paradigm.**
  Multi-stage programming and partial evaluation: a program specialised on what is known now, leaving a residue for later, cited from Taha, Multi-Stage Programming; Jones, Gomard and Sestoft, Partial Evaluation and Automatic Program Generation.
- **Grammar.**
  Deferral, and a deferred composition activated by a later run, each linked to its documentation section.
- **Specimen.**
  A tree at `docs/patterns/staged-compilation/`: an entry deferring a later-stage procedure, compiled as two runs.
- **What the bundle shows.**
  A first-stage bundle carrying the deferred target's path and none of its content, and a second-stage bundle carrying it, committed as the specimen's expected bundle set.
- **Principles.**
  The page's `Related` names the SOLID principles it serves: dependency inversion.
- **The limit to probe.**
  The page states whether a run can state which stage it is; a limit found is stated under `Limits` and raised as its own issue.

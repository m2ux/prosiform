## Overview

Continuous integration that runs every corpus fixture against the skeleton on each change.

## Problem

A corpus that runs only when someone remembers reports a regression after the change that caused it.

`make corpus` runs `pytest checks/tests`: the manifest schema cases, the catalogue cases and the runner's own unit tests. It executes no fixture of the corpus. `checks/runner.py` carries `run_fixture()` and nothing in the repository calls it over `checks/manifests.fixtures()`, so the 38 fixtures the corpus holds declare 38 expectations that no command verifies, and the suite is green.

Every count the walking skeleton has reported — 11 of 26, 30 of 32, 36 of 38 — came from a driver written by hand for one session and thrown away. The corpus's verdict has never been reproducible, and a figure nothing repeats cannot be regressed against.

## Proposal

The corpus is knowingly incomplete, and will stay so while the initiative's later epics land. Two fixtures declare behaviour no epic has delivered yet: one selects a nested section, which section extraction delivers, and one declares a root escape, which dependency traversal delivers. The second is the dangerous shape — the build exits 0 and publishes a bundle, so the fixture fails by succeeding. A corpus run that fails the change on any failing fixture therefore makes the tree red on the day it lands and stays red for two epics, which trains a reader to ignore it. A corpus run that passes regardless of failures states nothing. The rule separating the two is the design this task settles.

### The expectation lives in the fixture

A fixture that waits for later work declares what it waits for, in its own manifest:

```toml
awaiting = "I00:E03"
```

The value names the work that delivers the behaviour the fixture declares — initiative and epic, optionally the task — and the schema describes it as an optional top-level string with that shape. `fixtures/manifest.schema.json` is `additionalProperties: false` throughout, so the field is schema-described before a manifest may carry it, and `checks/tests/test_manifest_schema.py` holds that description.

Four outcomes follow, and two of them fail the run:

| Fixture | Run | Outcome | Fails the run |
| --- | --- | --- | --- |
| No marker | Meets its manifest | Pass | No |
| No marker | Differs | **Fail** | Yes |
| Marked `awaiting` | Differs | Awaited | No |
| Marked `awaiting` | Meets its manifest | **Unexpected pass** | Yes |

The fourth row is what makes the marker temporary. A fixture whose work has landed starts passing, and the run fails until the marker is removed, so the marker retires itself on the change that unblocks it rather than outliving it. Without that row a marker is permanent and nobody notices the day it stops being true, which is how a known-failure list rots.

### What this rejects

- **A list of excepted fixtures in the job definition or the Makefile.** The list sits in another file from the fixture it excepts, so a fixture renamed, moved or deleted leaves a line behind and a reader of the fixture sees nothing. It drifts silently, and silent drift between a declaration and the thing it describes is the state this task exists to end.
- **A bare boolean, `expected_failure = true`.** It says a fixture is excepted and not what would lift the exception, so a later session reads it as permanent. The marker names the work, so the session delivering that work is told which fixture to revisit.
- **A free-text reason.** Prose admits no check. A shape the schema states — `I00:E03`, optionally `I00:E03:W02` — can be read by a tool that asks which fixtures one epic unblocks.
- **Deriving the exception from the `clauses` a manifest already declares.** It would need a second table mapping each clause to the epic that delivers it, maintained outside the fixture, which is the drifting list again under another name.
- **Reporting an awaited failure as a pass.** An awaited fixture is reported as awaited, with the work it waits on, so the run's output states the corpus is incomplete rather than hiding it.

### The run

One command runs every fixture the corpus holds against the build under test, in path order, and prints a line for each, so the set it ran is visible rather than implied. A fixture that fails is named by the identity `checks/manifests.identity()` gives it — its path under `fixtures/` — and its differences follow it, so a red run names which fixture and where it differed rather than saying the corpus failed.

The build under test comes from configuration and from nowhere else: `PROSIFORM_BUILD` holds its command line, split as a shell splits one, and `checks/runner.py` raises when it is unset. The command treats that absence as a failure. A corpus run that skips because it found no build sits inside a passing suite saying nothing, and a fixture is never reported as holding against a build that never ran.

### Where it plugs in

The command joins `make check`, which is the one command a developer and the continuous-integration job both call, so the corpus runs on every change to the branches that carry the build without a second job or a second trigger. The job names the repository's own build through its console entry point, `uv run --project prototype --frozen prosiform`, so the corpus runs against the build the same change produced.

Two names would be confusable, so the names say what each one runs: `make corpus` runs the corpus against the build under test, which is what reading the words gives, and `make harness` runs the corpus harness's own tests — the manifest schema over every fixture, the catalogues against the design's text, and the runner's comparison. `checks/README.md`, the root `README.md` and `prototype/README.md` carry the command tables `make tables` holds in both directions, and each states the new meaning.

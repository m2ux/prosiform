**Component:** main:evals/diagram-following/baseline.json

## Overview

The committed default-matrix baseline carries a cell for every model, form and scenario the matrix runs, the bootstrap-audit scenarios among them, so each cell the eval measures has a recorded pass rate.

## Problem

- **The committed baseline covers less than the matrix builds.**
  A workflow written in the `bootstrap` form contributes scenarios the committed baseline carries no cell for, so those scenarios have no measured pass rate and no failure class of their own.

## Proposal

**The scene.** `matrix()` builds one session per model, workflow, scenario, form and repetition a harness can observe, and a run writes one cell per model, form and scenario in its `baseline.json`.

- **The matrix is the measure.**
  The run's cells are compared against the matrix the runner builds, so a scenario the matrix gives a harness appears in the committed baseline and one it withholds does not.
- **The gap is the missing form.**
  The cells the committed baseline lacks name the `bootstrap` form's scenarios, which the one committed harness observes and the baseline's earlier scope omitted.
- **The record follows a measured run.**
  The added cells come from a live run of the default matrix that follows `RUNBOOK.md`, and each failing session it records takes the triage rubric's disposition before the baseline is committed.

## Work Breakdown

| Part | Description |
| --- | --- |
| Analysis | Compare the committed baseline's cells against `matrix()` over the default forms, models and harnesses, and name each absent cell |
| Plan | The run's arguments, budget and the cells the committed baseline gains |
| Implementation | Run the default matrix live, triage its failing sessions and commit the reconciled baseline |
| Review | Every matrix cell has a cell, and no cell the matrix does not build remains |
| Test | `make harness` and the baseline-versus-matrix comparison |

## Overview

The command interface: its options, its two output streams and its exit statuses.

## Problem

Nothing executable exists, and without a declared split between bundled output and diagnostics a consumer cannot tell a published document from an error report.

The corpus harness decides a fixture's result from an invocation, a standard output, an exit status and a diagnostic stream. Until a command answers to those four, the harness runs nothing and every criterion that says *as the fixtures show* is unobservable.

Nothing beneath the command exists either. The option set, the stream split and the status categories are the whole of this task, and a run that names an entry reference reaches a compilation stage this task does not deliver. What that run does is a decision this task has to take rather than inherit, because the three statuses it could plausibly return say three different things about the build.

## Proposal

One command takes the allowed source root, the referring document, the output destination, the validation-only mode, the grouping rules and the diagnostic format. Bundled Markdown goes to standard output and diagnostics to standard error. Each outcome the design names returns its declared exit status.

### The Option Set

Every option the design's `## CLI contract` table declares is present and no option it does not declare is added. `--root` is the allowed source root; `--from` supplies the referring document a fragment-only reference needs; `-o, --output` names a file or `-` for standard output; `--group SLUG:DEPTH` is repeatable once per slug; `--check` validates without publishing; `--diagnostics text|json` selects the diagnostic format; `--version` and `--help` are informational.

The resource-limit options at `### Resource limits` — `--max-files`, `--max-file-bytes`, `--max-input-bytes`, `--max-output-bytes`, `--max-targets`, `--max-links`, `--max-nesting` and `--max-expansion-depth` — are **not** in this interface. Each is an override of a counting rule applied during discovery, parsing and emission, and none of those exists here; an option accepted and ignored is an interface that lies about what the build enforces. They arrive with the enforcement, in I00:E04, which owns the limits.

### The Stream Split

Standard output carries exactly one thing per run: the bundle, for a run that compiles one; the response, for an informational run; nothing at all otherwise. Diagnostics never reach it, so a caller that reads standard output reads either a document or an empty stream, and the exit status is the only signal it needs to tell which.

`--version` and `--help` write to standard output and return 0. The design makes an informational CLI response a success category of its own, distinct from a successful compilation, and `--help` exists to be read by a person who pipes it to a pager. AC3's *nothing else to that stream* governs a run that publishes a bundle: it forbids progress prose, byte counts and completion metadata accompanying the document, which is what the design's *Clean Markdown* rule forbids. It does not make the command's own response a diagnostic.

Standard error carries diagnostics in the format the run asked for, and that holds for a usage failure as much as for any other. The format is therefore read from the command line before the grammar is checked, so a run asking for JSON Lines never receives usage prose on the stream it is parsing. With `--diagnostics json` standard error carries one JSON object per line and nothing else.

### The Outcome a Reference Reaches

A run whose options are valid and which names an entry reference reaches the compilation stage. That stage is not part of this build, so the run publishes nothing and returns **4**, reporting on standard error that compilation is absent from the build rather than that anything is wrong with the source.

The two alternatives both state something untrue:

- **1 — an input, dependency, policy, safety or resource-limit failure.** The source is not at fault, and the design declares status 4 in the same sentence that forbids misreporting an internal condition as a source-document defect. A caller acting on 1 would go looking at its documents.
- **0 — a bundling path that is genuinely empty.** A successful run that compiled nothing is the truncated apparent success the design's *Agent delivery contract* exists to prevent, and *Completeness* forbids content being dropped to produce a result. It would also have to be taken back in W02, so it fails the standing rule that no stopgap is built to be replaced later.

Status 4 states what is true, needs no retraction — W02 replaces the stage and the status stops occurring — and leaves the three fixtures already in the corpus failing on their status rather than passing for the wrong reason.

No corpus fixture encodes it. A fixture declares a design clause, and *this build has no compiler yet* is a property of the build rather than of the contract; a fixture stating it would be deleted by the task that makes it untrue. The corpus also cannot express it: a manifest's diagnostic draws its code from the catalogue the design declares, and the design names no code for an unexpected internal error, because an unexpected error is by definition not one of the defects the contract defines. The outcome is held by unit tests in the build's own suite, which is where a statement about a build belongs.

### The Outcome-to-Status Mapping

| Status | Returned by |
| --- | --- |
| `0` | `--version` and `--help` |
| `1` | A source root naming no directory; a grouping rule whose slug names no directory under that root |
| `2` | A missing `--root`; no entry reference; a fragment-only reference with no `--from`; a grouping rule whose form or depth is wrong or whose slug repeats; an unknown `--diagnostics` value; an output path naming an input source |
| `3` | A write to standard output or to the output file that the stream refuses, a broken pipe among them |
| `4` | A valid run whose compilation stage this build does not carry |

A usage failure is reported before an input failure, whatever order the faults appear in: an invalid command line names no input that can be relied on. So the command checks the form of every option first, and only then looks for what the options name.

`E_INVALID_GROUP_RULE` is the one code this interface can emit, and the design gives it three causes: a depth outside 1 through 6, a slug given twice, and a slug naming no directory under the allowed source root. The first two are faults in the command line's form and return 2; the third is a fault in the tree the command line points at and returns 1, as a reference naming a missing document does. A code names a defect and a status names the category of its cause; the design states them as two axes, so one code deciding two statuses is the design working as written rather than an inconsistency.

The design declares no error code for an invalid CLI usage other than a grouping rule, and none for an unexpected internal error. Those diagnostics carry a severity and a message and no code, and the gap is raised as an arising issue rather than closed by inventing one.

### AC10, Half of Which This Row Cannot Observe

AC10 reads *a validation-only run bundles and validates its entry references and publishes nothing, to either stream or to a named output file*. Its two halves land on different rows, and this task delivers the one it can and declares the other unobserved rather than narrowing the criterion to fit.

- **Delivered and observed here.** `--check` is accepted with `--output FILE`, which the design makes explicitly legal and which is an option-combination decision this interface owns. A `--check` run writes no bundle to standard output, none to standard error, and creates no file at the path `--output` names.
- **Not observable here.** *Bundles and validates its entry references* needs discovery, parsing, emission and validation, which W02 through W04 deliver. A `--check` run at this row reaches the absent compilation stage and returns 4, so no run exists that validates anything.

The pull request therefore carries a test-plan row whose Test cell is empty, naming the unobserved half, which is the form a test plan takes for a criterion no check observes. The alternatives were rewording AC10 to what this row can hold, and moving it to the row that can observe it whole; both change a planned criterion to match a build's progress, and the empty-cell mechanism exists precisely so that it does not have to be changed.

AC3 and AC4 carry the same shape of partial observation and are recorded the same way. AC3's stream discipline is observed on every run this row can make, and *the bundle* on standard output waits for W04. AC4's statuses 0, 1 and 2 are observed by corpus fixtures, 3 and 4 by unit tests, since neither is expressible in a manifest: a broken pipe is not reachable through a runner that reads both streams, and an internal error has no catalogue code.

### The Documentation This Makes Untrue

The root README says nothing is built yet and that the build implements no behaviour. A command now exists, and what it does and does not yet do is what those passages must say.

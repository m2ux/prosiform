## Overview

The manifest schema opened to the warnings a run emits alongside success, and the link check widened from the READMEs to every document the repository owns outside the fixture corpus.

## Problem

A fixture declares the diagnostics its run produces, and `fixtures/manifest.schema.json` closes that declaration over the twelve error codes the design names. The design also describes two warnings — a grouping rule that arranges nothing, and a bundle whose resource references may not resolve where it is read — and a run emits each on a successful compilation. The schema's `severity` already admits `warning`, and its `code` is drawn from the error catalogue whatever the severity beside it says, so a manifest declaring a warning has to name an error code to validate. No fixture can state what a successful run writes to standard error.

The catalogue test holds the schema to the codes the design declares, and it collects `E_`-prefixed tokens alone. A warning code the design names is invisible to it, so the schema may omit one and every check still passes.

The link check reads the five READMEs and stops there. `docs/glossary.md` is read by no check that resolves a reference, although it ships inside the installed build and the tool's diagnostics draw their vocabulary from it, so a reference it gains is unheld from the moment it is written. The check also decides its own scope by a filename, so a document the repository adds outside a README is outside the check until the check itself is edited.

## Proposal

### A Warning Beside an Error

A diagnostic's severity decides which catalogue its code comes from. `severity` is already half of what names a diagnostic — `checks/runner.py` designates one by its severity and its code together — so the schema reads the same two fields as one key.

- **Two catalogues, neither admitting the other's codes.** `errorCode` enumerates the twelve codes the design declares with an `E_` prefix; `warningCode` enumerates the two it declares with a `W_` prefix. A diagnostic whose severity is `error` takes its code from the first and a diagnostic whose severity is `warning` from the second, so a manifest declaring a warning where an error belongs fails validation rather than stating the wrong contract. A warning accompanies a successful run and an error decides a failing one; a fixture that confuses them has declared a different run.

- **The pairing is a condition on the object, not two object shapes.** The diagnostic keeps one set of properties and one `additionalProperties: false`, with `severity` selecting the catalogue `code` is checked against. A second object shape would carry a second copy of `reference` and `source`, and a field added to one would be missing from the other.

- **The runner is unchanged.** It designates a diagnostic by severity and code, compares the declared sequence in order, and compares the further fields a manifest names. None of that reads a code's spelling, so a warning is compared as an error is.

- **`manifests.catalogue` takes the severity whose codes it returns.** The schema holds the one declaration of each catalogue, and the reader reaches it the way a diagnostic names it.

### The Catalogue Derived for Both Prefixes

`checks/tests/test_catalogue.py` reads the design from the branch and path the root README's Design link names, as the vocabulary check locates the same document, and that sourcing is unchanged: no path into a dated planning folder is written in a check. It collects each prefix the design uses and holds the matching catalogue to exactly the codes carried under it, so a code the design names that the schema omits fails the check whichever kind it is, and a code the schema carries that the design does not name fails it too.

### Every Document Outside the Corpus

`checks/documents.py` discovers every Markdown document git tracks, less those inside a fixture. A fixture is a directory holding `manifest.toml`, which is how `checks/manifests.py` finds one, and git lists those manifests alongside the documents, so the corpus names itself.

- **The boundary is the corpus, not a list of filenames.** A document added anywhere outside a fixture is read without the check being edited, and a fixture added anywhere is excepted without the check being edited.

- **The exception is what a fixture's sources are for.** `fixtures/*/*/source/` deliberately carries references a run is meant to refuse — `normalization/root-escape` exists because its source escapes the source root — so a check that resolved them would fail by design. `expected/` holds bundles, which are output rather than documents a reader follows.

- **`fixtures/README.md` is not corpus.** It sits above every fixture rather than inside one, and it is a document a reader follows, so it stays in the check as it already is.

- **The table check keeps the READMEs.** It compares the project's command and dependency tables with the `Makefile` and the project definition, and those tables are written in READMEs; its set is the READMEs among the documents, so one discovery serves both checks and each states its own scope.

### The Documentation the Change Makes Untrue

The root README's command table says the link check reads every README; `checks/README.md` says the same of `links.py` and says the catalogue test collects `E_`-prefixed codes; `fixtures/README.md` says the catalogue is closed over errors and that a warning cannot yet be declared. Each is brought to what the checks and the schema now do.

**Component:** `src/tests/test_cli.py` — the build's command cases.

## Overview

The outcome an error the contract does not name produces is observed directly: a run whose execution raises such an error returns the declared internal-error status and emits one error diagnostic carrying the declared code, and a case holds that in each of the two diagnostic formats.

## Problem

The command's generic handler catches whatever execution raises that the contract does not name, emits one error diagnostic under the declared internal-error code and returns the declared internal-error status. Nothing holds it to that. Three command-line cases once appeared to cover the status, but each named a fragment reference the build could not carry out, so each observed the section-selection stub standing in front of the handler; I00:E03:W02 delivered real selection and both the stub and those cases went.

What remains is a single case that breaks one of the build's own construction invariants and reads the outcome in one format only, so it states what happens when this build's provenance check disagrees rather than what happens when execution raises an error the contract does not name. A build returning the wrong status, emitting a diagnostic of the wrong severity or code, or emitting none at all, would pass every check the repository runs.

A corpus fixture cannot provoke it. A fixture declares a source tree and the bytes the run returns for it, and an unexpected internal error is a property of the run rather than of a source tree, so the catalogue entry stays what the design declares and the instrument is a unit case.

## Proposal

- **The case raises an error the contract does not name, from inside the run.**
  Execution is made to raise an error of a kind the contract names no outcome for, so what the case provokes is the generic handler's whole subject rather than one build-internal invariant that happens to reach it.

- **Both diagnostic formats are observed.**
  The format is chosen once for a run and every diagnostic is written in it, so an outcome observed in one says nothing about the other. One case reads the stream as a reader reads it and one reads it as the data a caller parses, and each asserts the status the run returned and the one diagnostic the stream carried.

- **The status and the code are read from the declaration, not spelled in the case.**
  The build declares the internal-error status and the unexpected-internal-error code, and the case names those declarations, so a build that renamed either fails the case rather than quietly satisfying a copy of its old spelling.

- **The severity is read where the stream carries it.**
  The data format carries the severity as a field of the diagnostic, so the case reading that format asserts it there. The reader's format renders a diagnostic under its code, which is the error catalogue's, so the case reading that format asserts the code the line is headed with.

- **Publication is observed with the outcome.**
  A run that fails this way publishes nothing to standard output, so each case states what both streams carried rather than the status alone.

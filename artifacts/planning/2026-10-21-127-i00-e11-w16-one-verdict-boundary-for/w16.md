**Component:** [`checks/links.py`](https://github.com/m2ux/prosiform/blob/main/checks/links.py)

## Overview

One function decides what every remote read of the link check says about its target, whether the read went out over the network or through the GitHub CLI.

## Problem

`checks/links.py` tells a host that said nothing from a reference that does not resolve. The boundary that draws the distinction is stated once in `checks/README.md` and spelled twice in code.

- **A direct read reads a number.**
  `verdict()` takes the integer status: 500 or above, and 403, are the host saying nothing; every other status of 400 or above is an answer the document is held to.

- **A tracker read reads a sentence.**
  `gh_api()` runs `gh api`, which prints its outcome as prose and keeps the status out of its exit code, so the module matches `HTTP (?:5\d\d|403)` against the last line `gh` wrote to standard error.

- **A change to the boundary reaches one spelling.**
  When 403 joined the statuses that say nothing, both spellings had to be found and changed by hand. An issue, a pull request or a project board is decided by a rule the README states for the other route, and the run passes or fails without naming the rule it used.

- **The second spelling rests on wording nobody here owns.**
  `gh` is free to reword `gh: Bad credentials (HTTP 401)`. Should the status stop appearing in that form, every tracker reference silently changes side.

## Proposal

The status a tracker call produced is recovered as a number and given to `verdict()`, so one function decides every remote read and `checks/README.md` describes both routes.

- **The status comes from the response, not from the message.**
  `gh api` is run with `--include`, which writes the response's own status line ahead of the headers. The number is read from that line, whose form the HTTP specification fixes, and the pattern over the CLI's prose goes.

- **A call `gh` reported no status for is the host saying nothing.**
  A command that timed out, or failed before a response arrived, carries no status line. That is a call that did not reach GitHub, which says nothing about the target for a reason of its own rather than a status to classify.

- **A failure the status alone calls resolved is still the failure `gh` reported.**
  A GraphQL call answers 200 and carries its errors in the body, so a project board that is not there arrives as a successful status and a failing command. The status decides every verdict it can state, and the reason `gh` gave stands where the status states nothing against the call.

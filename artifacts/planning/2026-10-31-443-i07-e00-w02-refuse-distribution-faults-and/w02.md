# W02 Refuse Distribution Faults and Entry Overwrite

> Work item · Delivered 2026-10-31

## Overview

Two faults that destroyed or obscured a run's own outcome: a dispatch link in an absorbed title, and a regular file standing where the run's folder belongs.

## Problem

A dispatch link in an absorbed document title indexes a missing placement key and raises a bare `KeyError` at exit 4. A regular file at `<entry>.bundles` is renamed aside and unlinked: exit 0, with unrelated bytes destroyed.

The finding is recorded as findings 4 and 18 in the [merged-epic review](../../2026-10-31-merged-epic-review/findings.md), with its site and the case that failed.

## Proposal

**The scene.** Each defect above was found by the review of fifteen merged epics, and each has a case that reproduces it. The task repairs one scope area and carries that case, so the defect cannot return unnoticed.

**The design.**

- **The repair follows the finding.** Refuse the dispatch link with a named code and a remedy, and refuse a path at `<entry>.bundles` that is neither a directory nor a symbolic link, leaving it untouched.
- **The case ships with the fix.** The failing case the finding records becomes a check the repository runs, so a regression fails a target rather than waiting for another review.
- **No other task's area is touched.** Each task repairs one scope and carries its own failing case, so the faults land as separate pull requests.

## Why an absorbed title cannot carry a dispatch

A dispatch sub-section stands one level below the section holding the link that names it, and the link then points at that sub-section's destination. A title the file heading absorbs is not emitted as a section: the file heading carries its text and the group keeps its source levels. The link is therefore still in selected content, and the dispatch map holds no entry for the region that writes it, because no section was placed for it.

The run indexed that map with the key the link names, which raised `KeyError` and reported `E_UNEXPECTED_INTERNAL_ERROR` at exit 4 — a fault the contract reserves for a defect in the tool. The defect is in the source: a title absorbs no dispatch sub-section, so the dispatch is one the bundle cannot state. It is now refused under `E_UNSUPPORTED_CONSTRUCT`, which is the code the contract already names for a construct the run cannot carry, with the link, its source line, the chain that reached it, and a remedy that names where a dispatch can be written.

The same key was unreachable from a merged group's member, where a title is absorbed by the subsection naming the member. That path is refused by the same check.

Probing the neighbouring shapes found a third, at a second site. Where a selection names a section beneath a title, the title stands above the selection and no group emits it at all: the file heading carries the title's text as literal heading text. Its link is therefore no link in the bundle, nothing places a sub-section for it, and the target is compiled by no run — so the dispatch vanished with the run reporting success and writing a bundle. That is the silent outcome the finding records, at its worst. The check reads the title's own inline text at that site and refuses it the same way.

| Shape | Before | After |
| --- | --- | --- |
| Entry document's own title | publishes, sub-section beneath the file heading | unchanged |
| Linked document's title | `E_UNEXPECTED_INTERNAL_ERROR`, exit 4 | `E_UNSUPPORTED_CONSTRUCT`, exit 1, a named refusal |
| Merged member's title | `E_UNEXPECTED_INTERNAL_ERROR`, exit 4 | `E_UNSUPPORTED_CONSTRUCT`, exit 1, a named refusal |
| A title above a selection | exit 0, the dispatch silently dropped and its target never compiled | `E_UNSUPPORTED_CONSTRUCT`, exit 1, a named refusal |
| A heading inside the body | publishes, sub-section one level below | unchanged |
| A deferred link in a title | rebases to the target's path | unchanged |

## Why a standing file is not an earlier set

The run folder is swapped in whole: the new set is written into a hidden folder beside it, whatever stands at the run folder's path is renamed aside, the new folder is renamed onto that path, and the earlier set is then removed. The rename and the removal are both `os.rename`, which moves whatever the path holds — a folder, a symbolic link, or a regular file.

A run that replaced a folder or a link was replacing what a run had written, which the contract states. A regular file there is material no run wrote, and the removal destroyed bytes the run never read while exiting 0. The path is now held to being a folder or a link before anything is written, so a file is refused with `E_PUBLICATION_FAILED` naming the path and a remedy, and is left exactly as it stood. The check runs under `-c`, as every other publication check does, so a check run refuses the same path a publishing run does.

# Joins and Ordering

Which rows take one pull request, and why the epics are ordered as they are.

## Within an epic

| Pair | Take one pull request because |
| --- | --- |
| A:W04 + A:W05 | Both are the boundary's consequence for one link. W04 states which links fail and W05 states what the boundary is; a branch carrying one and not the other either refuses every link above its file's directory or confines nothing. |
| C:W02 + C:W03 | The lookup and its two outcomes are one question: a folder key that answers for a reference has either a substitute to read or nothing, and the caller says which. |
| B:W03 + B:W04 | The fold that refuses a collision and the warning that reports an unused profile read one used-name set. |

## Across epics

| Edge | Consumes |
| --- | --- |
| A:W00 → B:W00 → C:W00 | Each clause amends the design after the previous pin moved, so the three pins are one chain rather than three branches amending one revision. |
| A:W03 → B:W02 | A profile governs a compilation's resolution, and resolution is the seam A:W03 moves. |
| A:W05 → C:W02 | A substitution reaches a substitute through the inclusion rule, so a folder of stubs is meaningful only once a stub declares. |
| C:W02 → B:W03 | A profile's entries reach one `Substitution`, and C:W02 is where that value holds two kinds of key. |

## Why this order rather than another

- **A first.** It narrows the key set B fills and moves the classification seam B reads. Delivering B first would mean writing the key rule twice, once against `root` and once against the declaration.
- **C second.** It is small, it amends a value A touched only to remove a parameter from, and B's demonstration needs a folder of stubs to point at.
- **B last.** It is the largest and the only one whose subject is a compilation rather than a source, and it reads both of the other two.

## What each epic's base is

Each epic cuts its base from `i05/main` after the previous epic's merge, so the clause pins chain and no epic branch carries another's frontmatter edits.

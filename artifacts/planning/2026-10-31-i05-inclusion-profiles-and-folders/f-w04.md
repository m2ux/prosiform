**Component:** fixtures/README.md

## Overview

The corpus states a fault as a manifest field, and the page says the runner translates it rather than a fixture naming a spelling.

## Problem

The page describes the fault in terms of the option.

- **The field's row names the option.** `fault` is documented as "the fault the run performs on itself, `source-changed`, `internal` or `cleanup-refused`, which the runner asks for as `-x NAME`".
- **A spelling in the page binds the corpus.** A fixture language naming one build's flag is a fixture language describing an implementation rather than a behaviour.
- **The manifest schema is unchanged.** The field keeps its three values and its optional status.
- **The three clauses still need a reason.** A reader meeting a `fault` field should learn why a run needs one, which is that some clauses state behaviour no tree produces.

## Proposal

**The scene.** `fixtures/README.md` documents each manifest field in a table, and `manifest.schema.json` validates a manifest against it.

**The design.**

- **The row states a behaviour.** `fault` becomes "the fault the run performs on itself, which the runner asks for by whatever means the build offers", naming the three values and nothing about a spelling.
- **The page says why it exists.** A sentence states that some clauses state behaviour no source tree can produce, so a fixture reaches them by asking the run to perform the fault.
- **The field's values are unchanged.** `source-changed`, `internal` and `cleanup-refused` remain the admitted set, and the schema already validates them.
- **The page names no build.** No flag, variable or environment is named, so the corpus binds the behaviour rather than the mechanism.

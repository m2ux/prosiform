**Component:** invocation.md

## Overview

The invocation and the source page state the profile: what a `prosiform` key may be, what a profile holds and what it governs.

## Problem

The documentation states one kind of `prosiform` key and a run-wide option surface.

- **`invocation.md` states the metadata block.** Its *Conversion metadata* section shows a `group` and `group-depth` example and states that the frontmatter declares root, group and depth.
- **`prosiform` admits three keys in the source page's table.** `docs/sources.md` lists `root`, `group` and `group-depth` with what each holds, and states that a key outside them fails the run.
- **Nothing states what an option applies to.** The option table's rows are properties of the run, and a reader has no word for the compilation a profile governs.

## Proposal

**The scene.** `invocation.md` holds a *Conversion metadata* section and an option table; `docs/sources.md` holds a *Frontmatter* section with a key table.

**The design.**

- **The key rule is stated once, in the source page.** `prosiform` admits an argument name, a profile name and its own fields; the table gains a row for each kind, and the empty block's meaning is stated beside them.
- **The profile's shape is shown.** `invocation.md` carries an example profile beside the group example, showing a name, a substitution pair and a budget override, and states the rule that selects it.
- **The term is defined where it is used.** *bundle compilation* joins the source page's account of what an entry reference reaches, so a reader meets the word before the rule that turns on it.
- **No new option row is needed.** A profile supplies values to options that already exist, so `make invocation`'s two-way comparison of the option table against the help output is unchanged.
- **Every statement of a root is already gone.** [Declared Inclusion](epic-a-declared-inclusion.md) rewrote those pages, so this task amends what that one left rather than repeating it.

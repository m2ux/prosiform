## Overview

The eval keeps a harness only where its agent CLI discovers skills natively, so every session it runs can start from a skill. Codex is the one harness in doubt: its bridge switches discovery off, and whether the CLI discovers a project's skills is established from its documentation here.

## Problem

- **Codex runs with discovery off.**
  The bridge sets `skills.include_instructions` and `features.skip_host_skill_discovery` against discovery, and its harness places a skill under `.agents/skills` that the session is never offered.
- **Its discovery is unestablished.**
  Nothing in the eval cites the Codex CLI's documentation on where it discovers a project's skills.

## Proposal

**The scene.** Four harnesses drive sessions: `claude`, `cursor` and `opencode` through their CLIs, and `codex` through an app-server bridge that verifies its configuration layers.

- **The documentation decides.**
  Codex stays where its CLI's own documentation states native discovery of a project skill root; the citation goes in the harness's docstring.
- **Kept, it discovers.**
  The bridge's configuration admits project skill discovery under the documented root and keeps the caller's and bundled skills out, and the bridge's tests hold both.
- **Retired, it leaves.**
  `codex_agent.py`, `stub_codex.py`, `test_codex_agent.py` and the `Codex` harness leave, with every README and `--harness` mention of them.

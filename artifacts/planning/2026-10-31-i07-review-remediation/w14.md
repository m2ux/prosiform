**Component:** example/work-planner

## Overview

Two example faults where a stated count is wrong and a demonstration names no repeatable revision.

## Problem

The example README states eighteen artifacts where the bundle it describes carries twenty. No document on `main` names the `demo/i02` revision a reader must repeat the demonstration on.

The finding is recorded as findings 30 and 31 in the [merged-epic review](../../2026-10-31-merged-epic-review/findings.md), with its site and the case that failed.

## Proposal

**The scene.** Each defect above was found by the review of fifteen merged epics, and each has a case that reproduces it. The task repairs one scope area and carries that case, so the defect cannot return unnoticed.

**The design.**

- **The repair follows the finding.** Derive each stated count from the artefact it describes at check time, and name the revision where the demonstration is taught.
- **The case ships with the fix.** The failing case the finding records becomes a check the repository runs, so a regression fails a target rather than waiting for another review.
- **No other task's area is touched.** Each task repairs one scope and carries its own failing case, so the faults land as separate pull requests.

## Work Breakdown

| Part | Description |
| --- | --- |
| Analysis | Read the finding and the site it names, and reproduce the case it records before changing anything. |
| Plan | Settle the repair against the surrounding code, and whether the case belongs in the corpus, the checks or the example, per the scope the disposition table names. |
| Implementation | Derive each stated count from the artefact it describes at check time, and name the revision where the demonstration is taught. |
| Review | Confirm the case fails before the change and passes after, and that no neighbouring behaviour moved. |
| Test | A run of the check that reads the count agrees with the bundle; a command run from the named revision repeats the demonstration. |

**Component:** src/prosiform/cli.py

## Overview

A run that publishes several bundles validates every one before it writes any, writes each atomically, and on any failure writes none. A caller then reads either the whole set a run produced or the set that was there before it, never a mixture.

## Problem

[`execute`](https://github.com/m2ux/prosiform/blob/9851615028ea489c48f6b3fa5ddbe0d917438cf2/src/prosiform/cli.py#L1909-L1996) composes, validates and publishes one bundle. [`publish_file`](https://github.com/m2ux/prosiform/blob/9851615028ea489c48f6b3fa5ddbe0d917438cf2/src/prosiform/cli.py#L1763-L1797) is atomic for that file alone, so a run of several bundles that fails on the third would leave the first two written beside stale copies of the rest.

## Proposal

A run compiles its entry and two dispatched targets; the second target crosses its budget.

- **Validate all, then write.**
  Every bundle is composed and validated before the first write; a failure in any ends the run with its diagnostic and writes nothing.
- **Each write is atomic.**
  Each bundle goes through the existing temporary-file-and-rename path.
- **`-c` writes nothing.**
  A validation-only run validates every bundle the run would publish and writes none.
- **Other files are left alone.**
  The run neither removes nor rewrites a file in the output folder it does not produce.
- **A write refused part-way.**
  A destination refusing a later write after earlier renames is `E_PUBLICATION_FAILED` naming that path; the design's Publication clause states what a reader can then find.

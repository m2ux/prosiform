## Overview

The declared Markdown profile, configured explicitly in the package, and the parse it produces over every source a run names.

## Problem

A default parser configuration is not the declared profile, and the difference changes whether a construct is a table, a strikethrough, a task marker or ordinary text.

`prototype/tests/test_profile.py` already shows the pinned parser *can* supply all five clauses the profile rests on, but it shows it by building `MarkdownIt("commonmark").enable([...])` inside a test helper. A configuration that exists only in a test is a claim about a parser, not a property of a build: nothing the command runs reads it, and the command reaches no parser at all.

The command therefore parses nothing. Every run whose options are valid raises the absent-stage failure W01 recorded, so a source the profile has no business accepting is indistinguishable from one it would publish. That is the gap this task closes, and it closes it before bundling exists, because bundling is stated over the parse.

## Proposal

`markdown-it-py` is configured to the profile in the package, the command reads and parses every source its entry references name under that configuration, and a source carrying a construct the profile refuses fails as the refusal it is.

### The Configuration, Clause by Clause

Each clause of `## Markdown and source-heading profile` is enforced by one named part of the configuration, and by nothing else. D6 records that the parser supplies these from its core, so no plugin is added and no preset wider than the profile is enabled.

| Clause | Enforced by |
| --- | --- |
| Core syntax | The `commonmark` preset, which is CommonMark and nothing further |
| Tables and strikethrough | The `table` and `strikethrough` core rules, enabled by name |
| Task lists preserved as text | The absence of the task-list plugin, which is what would replace a marker with a checkbox |
| Marker positions recognized | `linked_marker` and `unlink_marker`, which return a marker a reference definition has linked to the literal text it is |
| Typography off | The `commonmark` preset, whose typographer is off; nothing turns it on |
| HTML recognized so it can be refused | The preset's `html_block` and `html_inline` tokens, which `refusals` reads |
| Bare text infers no dependency | Recognition reading the parser's own tokens, so text the parser did not make a link is not one |
| Unsupported extensions | `refusals`, over the four constructs below |
| File suffixes | `is_markdown`, which lowercases the suffix and leaves the name's own spelling alone |

The configuration lives in `prosiform.profile` beside the `PROFILE` identifier `--version` already reports, so the pinned configuration and the version it is pinned to are one thing. A later extension change that reinterpreted existing source would have to change this module, and the suite here would report it.

A reference definition can otherwise make a task marker a dependency, which is the hazard the profile's *recognize marker positions* clause names. The pinned parser does exactly that: with `[x]: page.md` in the document, `- [x] done` parses as a link to `page.md`. The parse recognizes the position — the head of a list item's first paragraph, the marker followed by whitespace or nothing — and returns the marker to text, so the token stream every later stage reads carries no such link, and the marker survives as the three characters the source wrote.

### Where Recognition Stops

The design states both halves: reject a **recognized unsupported dependency or section-naming construct** in selected content, and **do not guess every possible extension from ordinary prose**. The rule that separates them is two conditions, and a construct is recognized only when both hold.

1. **The parser left the spelling as text.** Recognition reads the text children of an inline token and nothing else, so a code span, a fenced or indented code block, a link destination, an autolink and raw HTML carry none of it. This is what makes prose *about* a wiki link, and a regular expression `[^abc]` in a code span, ordinary content.
2. **The source spelled it unescaped.** The same pattern must match the raw source the parser read, where an escape is still a backslash. An author who writes `\[\[page\]\]` has said the text is literal, and the profile takes them at their word.

What is recognized is the set of constructs spelled inside Markdown's own link and heading syntax, because those are the spellings whose meaning is a name:

| Construct | Spelling | Names |
| --- | --- | --- |
| Wiki link | `[[target]]` | Another document |
| Transclusion directive | `![[target]]` | Another document, to be inlined |
| Footnote reference | `[^label]`, a definition's leading `[^label]:` included | A target within the document |
| Heading attribute | `{#id}` at the end of a heading's text | The section that heading opens |

What is **not** recognized, deliberately:

- **A brace block anywhere but the end of a heading.** `{#custom-id}` in a paragraph names no section; recognizing it would fail prose that discusses the syntax.
- **A heading attribute that is not an identifier.** `{.class}` and `{key=value}` are heading-attribute syntax the profile does not support, but neither names a dependency nor a section, so neither is a construct the rule covers. They reach the bundle as the text they are.
- **A directive in a templating language.** `{% include %}`, `{{ include }}` and the rest are not Markdown, and recognizing them means guessing at a language the profile does not read. They are ordinary prose.
- **A bare path or URL in prose.** The profile says so directly, and nothing here infers a dependency from one.

A rule only ever observed firing is a rule whose other half nobody tested, so every construct above is tested in both directions: the construct refused, and the code span, the escape, the code block and the paragraph that resemble it passing untouched.

### The Fate of the Absent-Stage Placeholder

W01's placeholder is narrowed, not removed, and its honesty is kept.

Reading a source and parsing it is not bundling it. W04 emits the bundle, so a run whose sources the profile accepts still legitimately ends at a stage this build does not carry, and still returns **4** saying so rather than claiming a source is at fault. What changes is what reaches it: the run now resolves, reads and parses every entry document first, so a source the profile refuses fails at the refusal with status **1** and a diagnostic naming the construct, the reference it spells and the line it sits on. The placeholder's message states what the build does — it reads and parses the sources its entry references name, and carries no bundling stage — which is the stage boundary as it now stands.

Removing the placeholder was the alternative, and it would mean a run returning 0 having published nothing, which is the truncated apparent success the *Agent delivery contract* exists to prevent and which W01 rejected on the same grounds.

### Selected Content, Until Selection Exists

The profile refuses a construct **in selected content**. Section selection is a later epic, so the only selection this build can make is the whole document. Each entry document a run names, the referring document `--from` supplies included, is read and scanned whole, and a fragment narrows nothing yet. The scan therefore reaches content a narrower selection would exclude; it never reaches a document the run does not name. When extraction lands, the scan runs over the selected regions and this paragraph is what it narrows.

### The Refusals the Contract Has No Code For

Three failures this task introduces have no code in the catalogue, and none is invented here.

| Failure | Code | Status |
| --- | --- | --- |
| An entry reference whose suffix is outside the profile | None | 1 |
| Raw HTML in selected content | None | 1 |
| A recognized unsupported dependency or section-naming construct | None | 1 |
| An entry reference normalizing outside the allowed source root | `E_SOURCE_OUTSIDE_ROOT` | 1 |
| An entry reference naming no document under that root | `E_TARGET_NOT_FOUND` | 1 |

The last two are catalogued failures this task can name, and it names them: a run that reads files has to enforce the root it was given, and a document that is not there is a reference resolving to nothing.

The first three carry a severity and a message and no code, as the contract requires of a defect it does not declare. They are reported to W07, which is the row that declares the codes the contract lacks, and they widen the list that row already carries. Until then the refusing direction of AC7 and AC9 has no corpus fixture: a manifest requires a catalogued code for every diagnostic it declares, so a fixture for these refusals cannot state the run it means. Those directions are held by unit tests, which is where a statement the corpus structurally cannot express belongs.

### The Fixtures This Row Adds

The `Profile` family the design's `## Adversarial acceptance fixtures` names — *task markers protected from definitions, disabled typographic rewriting, Markdown suffix classification, and explicit rejection of unsupported selected dependency constructs* — gains four fixtures, each declaring the result the contract names rather than the result this build currently produces:

- `profile/task-markers-and-typography` — markers and substitution-bait punctuation reaching the bundle as written.
- `profile/task-markers-protected-from-definitions` — a definition labelled `[x]` turning no marker into a link, and leaving no definition in the bundle.
- `profile/extension-lookalikes` — the code span, the escape, the paragraph brace block and the fenced example bundling untouched.
- `profile/html-in-a-code-example` — HTML inside a code block bundling byte for byte.

Each expects status 0 and the bundle W04 emits, so each fails today on its exit status exactly as the three fixtures already in the corpus do, and each passes when the bundling stage lands. Suffix classification is the family's fourth case and has no fixture for the same reason the refusals have none: the failure it declares has no code.

### The Documentation This Makes Untrue

The root README says a run that names an entry reference returns 4. A run now returns 1 for a source the profile refuses, and the README says which sources those are. The prototype README describes `tests/test_profile.py` as holding the pinned parser to five clauses; it holds the build's own configured parser to those clauses and to the recognition rule's two directions.

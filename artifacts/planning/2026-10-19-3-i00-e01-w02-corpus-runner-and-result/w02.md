## Overview

The runner that executes one fixture, the comparison that decides its result from the manifest and the fixture's files alone, and the difference reporting that names which expectation differed and where inside it.

## Problem

A declared fixture produces no verdict. `fixtures/` holds three fixtures and a schema that describes them, and `checks/manifests.py` reads and validates one, but nothing runs one. The corpus states the contract and reports nothing when an implementation departs from it.

A comparison that reports only a mismatch does not locate it. Standard output is the whole bundle: a run that differs in one byte and a run that differs in every byte produce the same verdict, and the preservation invariant turns on exactly the bytes a text comparison hides — the spelling of a newline and whether the document ends with one. A diagnostic list has three ways to be wrong that a length check and an equality check cannot tell apart: one missing, one extra, and the expected ones in the other order.

The runner is also where language-neutrality stops being a claim about the schema and becomes a property of running code. A runner that imports the Python package, knows its flags or matches its internal wording makes the corpus a test of one implementation, and the production build in Rust inherits assertions rather than a contract.

Nothing can be invoked yet. `prototype/src/prosiform/` is a docstring; the compiler starts in E02. A runner written against a build that does not exist either waits for one or quietly reports success in its absence.

## Proposal

The runner is one module beside the reader W01 left, `checks/runner.py`, and `run_fixture(fixture)` is the whole of its interface. It reads the manifest through `checks/manifests.py`, invokes the build under test against the fixture's source tree, compares all three declared expectations, and returns a `Result`.

- **The build under test is configuration, and the runner invokes it as a subprocess.**
  The environment variable `PROSIFORM_BUILD` holds a command line, split as a shell splits one, so a build reached through a wrapper or an interpreter is named in full. The runner imports no package, names no module and names no language: it appends `--root`, the fixture's source tree resolved to an absolute path, and `--diagnostics json` to that command, then the manifest's `arguments`, and reads back bytes and a status. `--root` and `--diagnostics json` are the contract's own command line, which every implementation honours, and W01 settled that the runner supplies them so a diagnostic's code is comparable as a value.

- **An absent build is refused, not passed.**
  There is no default command and no fallback to an installed package. `build_under_test()` raises `BuildNotConfigured` when the variable is unset or blank, so a caller gets an exception rather than a verdict. This is what keeps the arrangement from becoming a hole: the only way a fixture reports as holding is for a configured command to have run and produced the declared result.

- **The runner's tests supply their own build and their own fixtures.**
  Each test writes a fixture into a temporary directory — manifest, source tree and expected bytes — and validates it against the corpus schema before using it, so the runner is exercised on real manifests. The configured build is a canned program that replays bytes on standard output, bytes on standard error and an exit status; one test configures `/bin/true` and `/bin/false`, which are not the tool at all. No test runs a corpus fixture, so no fixture's expected bytes stand in as a result they were never compared against, and `identity/whole-document` remains what W01 left: a reading of the design that no run has confirmed.

- **A malformed fixture fails as a fixture, before any build runs.**
  The runner validates the manifest through `errors` and `missing_files` first. A fixture the schema does not describe returns a difference naming the manifest, and the build is not invoked, so a schema fault is never reported as a behavioural one.

- **Standard output is compared as bytes and located by byte offset.**
  The expected bytes come from the file `expected.stdout` names, and nothing decodes either side. A difference reports the length of each, the offset of the first differing byte, the line and byte column that offset falls on, and a window of each side rendered with its control bytes spelled out, so a CRLF against an LF is two visibly different windows rather than two identical lines. When one side is a prefix of the other the report says so by name, which is the trailing-newline case.

- **Diagnostics are compared in order, on the fields the manifest declares.**
  A diagnostic is named by its `severity` and `code`. When the sequence of those names differs, the report distinguishes the three cases: the same diagnostics in another order are reported as an ordering difference carrying both orders, and otherwise each position is reported as a mismatch, a diagnostic the run did not emit, or one no expectation declares. Where the names agree, the further fields the manifest declares — `reference` and `source` — are compared and reported by field with both values. A run carrying a `message` or a `remedy` the manifest does not name still matches, because the manifest binds what it declares. A standard error line that is not a JSON object is reported as one, since the declared format carries diagnostics and nothing else.

- **Nothing in the runner enumerates a code.**
  A diagnostic's name is built from the values the run and the manifest carry. W05 adding warning codes to the schema needs no change here: a warning is a diagnostic whose severity is `warning`, and severity is already half of the name every comparison keys on.

- **The result is one shape, and W03 consumes it.**
  `Result` carries the fixture's identity — its path under `fixtures/`, which `manifests.identity` now supplies to the runner and to the corpus test alike — a tuple of `Difference`, the exit status, and the two captured streams. `passed` is the absence of differences. `report()` renders the verdict as the fixture, then each difference as its expectation, its summary and its located region. A `Difference` names the manifest field it belongs to: `expected.stdout`, `expected.exit_status`, `expected.diagnostics`, `invocation` for a run that did not complete, and `manifest` for a fixture the schema does not describe.

- **A run that does not complete fails the fixture.**
  `PROSIFORM_BUILD_TIMEOUT` bounds a run in seconds, defaulting to sixty. A build that hangs returns a difference naming the invocation rather than hanging the corpus.

### Holding the Runner to AC2

A test cannot establish that a module names no implementation; it can only catch the names it was told about. Three things hold the criterion together.

- **The read.** The runner is read line by line for anything it assumes about what it invokes. That read is recorded in [validation.md](validation.md).
- **The mechanical guard.** `test_the_runner_names_no_implementation_or_language` reads `checks/runner.py` and fails on any of `python`, `pytest`, `pyproject`, `prototype`, `cargo`, `rust`, `node`, `npm`, `src/prosiform` or `import prosiform`. It catches the obvious regression, and the module carries no shebang so the guard is not satisfied trivially. `PROSIFORM_BUILD` names the product, which both builds are, not an implementation of it.
- **The demonstration.** A test configures the build as `/bin/true` and then `/bin/false` over one fixture and gets a pass and then a failure, so the verdict follows configuration and the program invoked need not be prosiform at all.

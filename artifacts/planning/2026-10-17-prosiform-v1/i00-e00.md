## Overview

The repository holds a placeholder and nothing else. This epic lays out the trees this stage needs, establishes a Python environment whose dependencies resolve to pinned versions, makes tests and static checks runnable from documented commands that continuous integration also runs, and states in the README what the project is. Every later task lands in the structure it creates.

## Problem

The plan assumes a repository that does not exist yet, so its first task has nowhere to land.

- **The default branch is a placeholder.**
  `main` holds a README whose body is `tbd` and no other file, so there is no tree, no package and no test to extend.

- **The planned layout lives only in a decision.**
  The record names separate trees for the fixture corpus and the Python build, and nothing in the repository realizes that separation.

- **Nothing pins what the build runs on.**
  The prototype's parser is decided and unpinned, so two checkouts can resolve different parser versions and disagree about what a document means.

- **Tests have no runner.**
  Every later epic carries tests, and nothing states how they are discovered, how they are run, or what reports a failure.

- **A reader finds no account of the project.**
  The design and the plan sit on another branch, and nothing in the default branch says what the tool is or points at them.

- **The contract's vocabulary lives nowhere a user can read it.**
  The design names a closure, a region, a structural ancestor, a variant and a destination, each meaning one thing and nothing else. A reader of the tool meets those words in its diagnostics and its documentation with no definition to hand, and a later author has nothing to keep the usage from drifting.

## Proposal

- **The trees this stage needs.**
  One tree for the language-neutral fixture corpus, one for the Python build, and one for the documentation the repository owns. The production build's tree, toolchain and dependencies are created by the initiative that writes that build, so nothing here stands empty waiting for it.

- **One Python environment, resolved to pinned versions.**
  A project definition declares the runtime version and the dependencies, and a lockfile records the exact resolved versions a checkout installs, so parser behaviour does not vary between checkouts.

- **Documented commands run the checks.**
  Tests, lint, format and type checks are each a named command. Continuous integration runs those same commands rather than its own variants, so a check cannot pass locally and be absent remotely.

- **The README is the way in.**
  What the tool does, how it is installed, how it is invoked, and links to the design and the plan on the branch that holds them.

- **The glossary ships with the tool.**
  One definition for each term the contract uses, in the documentation tree, published with the build rather than kept in the planning record. The design, the acceptance criteria, the corpus and the tool's diagnostics draw their vocabulary from it, so a term means one thing across all four.

- **Documentation is linked, not copied.**
  The documentation tree holds what the repository owns. The design and the planning record stay on the engineering branch and are referenced, so there is one copy of each.

## Overview

Corpus conformance turns a passing build into a measured contract. The adversarial fixture families the design names are completed, every behavioural clause is mapped to the fixtures that exercise it, any clause no fixture covers is listed as uncovered, and the corpus and its report are checked for independence from any implementation. This is the artifact the production build inherits.

## Problem

A corpus that passes says what was tested, not what the contract requires.

- **Coverage is assumed, not measured.**
  Fixtures accumulate alongside the work that needed them, so a clause nobody implemented has no fixture and no record that it has none.

- **An absent fixture is invisible.**
  A clause with no fixture produces no failure, so the gap presents as a passing corpus.

- **Fixtures written beside one build inherit its assumptions.**
  A fixture naming a module, a flag spelling or an error-message wording specific to one implementation binds that implementation rather than the contract.

- **The adversarial cases are a list in prose.**
  The design names families of hard cases, and a family nobody turned into fixtures is a family the next implementation meets for the first time in production.

## Proposal

- **Each named family becomes fixtures.**
  Identity, coverage, destinations, references, extraction, boundaries, file hierarchy, partial outlines, normalization, resources, consistency, validation scope, generated inputs, delivery, parser fidelity, definition inventory, profile, frontmatter, command interface and limits each have fixtures in the corpus.

- **Clauses map to fixtures.**
  Each behavioural clause of the design carries the identifiers of the fixtures that exercise it. The mapping is generated from the corpus and the design rather than maintained by hand.

- **The declared names are exercised, not merely referred to.**
  The criteria bind to the error code and exit status the design declares rather than repeating the names, so nothing otherwise requires the build's set to be the design's. The report compares them, and a code the build emits that the design does not name, or a declared outcome no fixture produces, is a reported failure.

- **An uncovered clause is reported, not dropped.**
  A clause with no fixture appears in the report's uncovered list, so a gap is a visible result of running the report.

- **Independence is checked.**
  The corpus and the report are checked for references to an implementation language, module or internal error wording, so what they bind is the behaviour.

## Acceptance Criteria

- [ ] **AC1.** Each adversarial fixture family the design names has fixtures in the corpus, as the conformance report's family listing shows.
- [ ] **AC2.** Each behavioural clause the design states carries the identifiers of the fixtures exercising it, as the conformance report's mapping shows.
- [ ] **AC3.** A clause with no fixture appears in the report's uncovered list, as the report run against a deliberately unfixtured clause shows.
- [ ] **AC4.** No fixture or report entry names an implementation language, module or internal error wording, as the independence check shows.
- [ ] **AC5.** The error codes the build emits are exactly those the design declares, and each declared exit status is produced by at least one fixture, as the conformance report's declared-surface listing shows.

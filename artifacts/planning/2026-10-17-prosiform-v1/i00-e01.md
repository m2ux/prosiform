## Overview

The corpus harness is the instrument every later criterion in this initiative names. It defines how one fixture declares its sources, its invocation and its expected result, and it supplies the runner that decides pass or fail from that declaration alone. It exists first because a contract that cannot be executed cannot be violated visibly.

## Problem

The behavioural contract exists only as prose, and prose reports nothing when an implementation departs from it.

- **A clause cannot fail.**
  The design states invariants about bundled output, failure behaviour and limits. None of them produces a signal when the output is wrong.

- **A test written against one build binds only that build.**
  Checks expressed in a language's test framework carry that language's assumptions, so a second implementation inherits assertions rather than a contract.

- **A bundling failure has several observable parts.**
  Standard output, exit status and the diagnostic stream each carry part of the result, so a check reading only one of them passes a bundling that failed in the others.

## Proposal

- **A fixture is a directory with a manifest.**
  The directory holds the source tree the fixture bundles. The manifest names the invocation, the expected standard output, the expected exit status and the expected diagnostics, including their error codes. The catalogue of those codes is declared with the schema.

- **The manifest is the whole declaration.**
  The runner reads the manifest and the fixture's files, runs the declared invocation against a build identified by configuration, and compares every declared expectation. It holds no knowledge of any implementation.

- **The failure names belong to the schema.**
  The error codes the design declares are part of the manifest schema, so a fixture expecting a failure names one of them and a manifest naming anything else is rejected as malformed.

- **A failure names the differing region.**
  A mismatch reports which expectation differed and where, so a corpus failure identifies the defect rather than reporting only that a comparison failed.

- **Continuous integration runs the whole corpus.**
  Every change runs every fixture, so a regression surfaces on the change that caused it.

## Acceptance Criteria

- [x] **AC1.** A fixture declares its source tree, its invocation, its expected standard output, its expected exit status and its expected diagnostics in one manifest, as the schema validation test shows.
- [x] **AC2.** The runner decides a fixture's result from its manifest and files alone, naming no implementation module or language, as the runner's unit tests show.
- [x] **AC3.** A mismatched expectation is reported with the expectation that differed and the differing region, as the runner's failure tests show.
- [x] **AC5.** A manifest naming an error code outside the declared catalogue fails schema validation, as the schema tests show.
- [x] **AC6.** The build README's dependency and command tables name what the project declares and nothing it does not, as the README check shows.
- [x] **AC7.** A fixture declares the warnings its run emits, and a manifest naming a warning code outside the declared catalogue fails schema validation, as the schema tests show.
- [x] **AC8.** Every reference in every document the repository owns resolves, the fixture corpus excepted, as the link check shows.

## Overview

Corpus migration makes the production build what the repository's own checks prove. The corpus runner, the repository checks and continuous integration run the Rust binary by default, and the prototype runs where it is named, so a passing run is evidence about the build callers will be given.

## Problem

The checks that guard every change exercise the prototype.

- **The runner invokes the Python entry point.**
  The corpus runner bundles each input with the installed Python command, so the production build is proven only where the differential run reaches it.

- **The repository checks name the prototype.**
  The invocation, smoke and conformance checks run the Python command, so its help, exit statuses and diagnostics are what the documentation is held to.

- **Continuous integration gates on the prototype.**
  A change that breaks the production build alone fails no required job.

## Proposal

- **One selector names the build.**
  The runner and the checks take the build under test from one setting, the production binary by default and the prototype where it is named.

- **The checks follow the selector.**
  Each check that invokes the command runs it through that setting rather than through a fixed entry point.

- **The production build is the required job.**
  Continuous integration fails a change on a production-build corpus or check failure, and the differential job carries the prototype.

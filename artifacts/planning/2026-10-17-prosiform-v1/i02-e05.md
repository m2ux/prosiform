## Overview

Validation and delivery close the production build: the candidate validation mode and its provenance invariants, boundary safety, source-change detection, generated-input rejection, the diagnostic shape and its JSON form, the command interface, and the delivery contract that makes a partial transport a reported failure rather than an apparent success.

## Problem

A compilation that validated is not yet a bundle the calling agent received.

- **Surface validity proves nothing about provenance.**
  A candidate that parses can still omit a selected region or carry a destination that points somewhere else.

- **A boundary can swallow what follows it.**
  Regions joined without safe separation can place later content inside an earlier fence, HTML block, list or quote.

- **Standard output is not an atomic delivery.**
  A broken pipe or a transport limit can truncate a bundle that compiled correctly, and Markdown arriving is not evidence that all of it arrived.

- **A failure the agent cannot explain is a failure twice.**
  Without a code, a location, the offending reference and the inclusion chain, a calling agent can report only that bundling failed.

## Proposal

- **Candidate mode has its own policy context.**
  Generated filename headings, shifted headings and structural ancestors are expected; frontmatter stripping, dependency discovery and generated-input rejection do not run on the candidate.

- **Invariants are checked against recorded provenance.**
  Destination integrity, exactly-once coverage, absence of new links, absence of surviving definitions, ownership stability, outline preservation and depth safety are checked against provenance ranges and generated-structure records.

- **Publication is atomic and gated.**
  File output is written atomically after validation, and an output that would overwrite an input source is refused.

- **Delivery failure is reported, not disguised.**
  A detected broken pipe or write failure returns its declared exit status, and no oversized output is replaced with a summary or a partial document.

- **Diagnostics carry a stable shape.**
  Code, referring source location, original reference, resolved identity where one exists, inclusion chain and a remedy where one can be stated accurately, with one JSON object per line when that format is selected.

## Acceptance Criteria

- [ ] **AC1.** A candidate disagreeing with its recorded source provenance publishes nothing and fails, as the corpus's validation fixtures show.
- [ ] **AC2.** A region boundary that would place content inside an unintended container fails with its declared error code, as the corpus's boundary fixtures show.
- [ ] **AC3.** A source whose content or canonical identity changes during compilation fails with a retry diagnostic, and a source whose links carry bundle destinations is rejected, as the corpus's consistency and generated-input fixtures show.
- [ ] **AC4.** Each diagnostic carries a stable error code, the referring source location, the original reference, the resolved identity where one exists and the inclusion chain, as the corpus's diagnostic fixtures show.
- [ ] **AC5.** The command returns the declared exit status for each outcome the design names, as the corpus's exit-status fixtures show.
- [ ] **AC6.** A detected broken output pipe or write failure returns its declared exit status rather than reporting success, and no bundle is replaced by a summary or a partial document, as the corpus's delivery fixtures show.
- [ ] **AC7.** A successful run reports each entry reference and the destination it resolved to on the diagnostic stream, under a grouping rule as without one, as the corpus's delivery fixtures show.

## Overview

The repository's trees, the README that explains what they are for, and the glossary the contract's vocabulary comes from.

## Problem

The default branch holds a placeholder README and no other file, so the separation the plan assumes between the corpus and the Python build exists only in a decision. The vocabulary the contract depends on lives nowhere a user of the tool can read it, so a reader meets a closure, a region, a structural ancestor and a variant in the diagnostics with no definition to hand.

## Proposal

Three trees are created: one for the language-neutral fixture corpus, one for the Python build, and one for the documentation the repository owns. The production build's tree is not created here; the initiative that writes that build creates it. The README states what the tool does, how it is installed, how it is invoked, and links to the design and the planning record on the engineering branch rather than copying them. The documentation tree holds a glossary defining each term the contract uses, published with the build, and the design, the criteria, the corpus and the diagnostics draw their vocabulary from it. A layout check asserts the trees exist, a link check asserts the README's references resolve, and a vocabulary check asserts every contract term the design and the criteria use is defined in the glossary.

## Work Breakdown

| Part | Description |
| --- | --- |
| Analysis | The trees this stage needs and what belongs in each |
| Plan | The layout, the README's sections, the glossary's entries and the three checks |
| Implementation | The trees, the README, the glossary and the checks |
| Review | Confirmed that no design or planning content is copied rather than linked, and that no tree is created for a build this stage does not write |
| Test | The layout check fails on a missing tree, the link check fails on an unresolvable reference, and the vocabulary check fails on a contract term the glossary does not define |

## Overview

Continuous integration running the same commands a developer runs.

## Problem

A check that exists only locally passes silently when it is skipped, and one that exists only remotely cannot be reproduced before a change is pushed.

## Proposal

A continuous-integration job installs the environment from the lockfile and runs the documented check commands, failing the change when one of them fails. It invokes those commands rather than reimplementing them, so a local run and a remote run exercise the same configuration.

The link check reaches the project board the README names, which is a user-level project the job's built-in token cannot read. The job supplies a token carrying `read:project` from repository secrets, so the board link is checked remotely as it is locally.

The slug a heading yields is the one GitHub generates, including for a heading opening with an emoji, so a fragment link that resolves in the check resolves on GitHub.

## Work Breakdown

| Part | Description |
| --- | --- |
| Analysis | The job environment, how it obtains the locked dependencies, and the credential the link check requires |
| Plan | The job's steps, each naming a documented command, and where its token comes from |
| Implementation | The job, its wiring to the lockfile and the commands, and the link check's slug rule brought to GitHub's |
| Review | Confirmed that the job runs the documented commands rather than its own variants |
| Test | A deliberate violation of each check fails the job, and the clean tree passes it; a heading opening with an emoji yields the slug GitHub generates |

**Component:** [`checks/runner.py`](https://github.com/m2ux/prosiform/blob/main/checks/runner.py)

## Overview

A fixture gains a way to state the text a run's output carries, so an outcome whose exact bytes belong to one build is still stated by the corpus. Standard output is declared either as the bytes a run must reproduce or as the text it must carry, and a diagnostic declares the text its message carries, so two faults sharing one error code are told apart.

## Problem

Every comparison the runner performs is an equality, and two outcomes the contract defines cannot be stated as one.

- **An informational response carries a version string.**
  `--version` reports the tool version and the profile identifier. The version belongs to the build, so a file of expected bytes would bind the corpus to one implementation, and no fixture states the response at all.

- **One error code names several distinct faults.**
  `E_INVALID_USAGE` names every command line the grammar does not admit. Three fixtures declare the same severity, code and exit status for three distinct faults, so each passes against the other's run and a build reporting the wrong fault records conformance.

- **The message is the only thing that separates them, and nothing reads it.**
  The runner compares a diagnostic on severity, code, reference, resolved, source and chain. A build answering "no entry reference" where the fault was a fragment-only reference with no referring document passes every fixture in the corpus.

## Proposal

The corpus already states what an outcome must be; it gains a way to state what an outcome must carry. One declaration shape serves both sites, so the question is settled once rather than per field: a list of text, each entry a substring the output must contain. A substring names the part that identifies the outcome and leaves every build its own wording, which is what a whole message or a whole stream cannot do.

- **Standard output is declared one way or the other.**
  `expected.stdout` names a file of bytes, as it does today. `expected.stdout_contains` names the text the stream must carry instead. A manifest declares exactly one of them, so a fixture never half-states its output and no run goes uncompared.

- **A diagnostic declares the text its message carries.**
  `message_contains` is an optional field beside `reference`, `resolved`, `source` and `chain`. A declaration absent compares nothing, so every fixture now in the corpus stays valid, and a fixture adds it where its code alone does not identify the fault.

- **A difference names what was missing and shows what arrived.**
  A stream or a message that does not carry a declared entry is reported under the expectation it belongs to, naming each entry absent and the text produced, so a failure locates itself the way a byte difference does.

- **The three usage fixtures state their faults.**
  Each of the fixtures sharing `E_INVALID_USAGE` declares the text identifying its own fault, so the run of one fails against the diagnostic of another.

- **The informational response becomes a fixture.**
  A fixture runs `--version`, declares exit status 0, no diagnostics, and the two things the contract says the response reports: the tool's name and the profile identifier. The version between them is the build's own.

## Overview

Installation of the build and the entry point callers depend on.

## Problem

The command runs only from a checkout, so every caller resolves the build's location for itself.

## Proposal

The build is packaged so it installs into an environment and exposes one documented command name. The entry point is resolvable without knowing where the repository sits, and reports its version and profile identifier.

## Analysis

A caller in this workspace is an agent running a shell whose working directory is wherever its own work sits. It resolves a tool by name, through `PATH`, and it carries no knowledge of where this repository is checked out — or whether it is checked out at all.

Three properties follow, and together they are what makes a command an entry point rather than a script someone runs from a tree:

- **Named on the path.** The installation puts one documented name in the environment's executable directory. A caller writes the name; nothing resolves a path for it.
- **Independent of the working directory.** The run's outcome depends on the options it is given and the source root they name, and on nothing about where the process was started.
- **Independent of the repository.** The installed build carries everything it reads, the glossary its diagnostics draw vocabulary from included. A caller's source root is its own tree, unrelated to this one.

The packaging metadata already declares the console entry point, `prosiform = "prosiform.cli:main"`, and the command already answers `--version` with its version and the profile identifier. What the repository has never had is an instrument that observes the three properties above. Every run of the build in the checks today goes through `uv run --project prototype`, which names the checkout, so a packaging change that broke installation would pass the whole gate. The row's deliverable is therefore the proving instrument and the documentation it makes true, not a second entry point.

## Design

### The installation smoke run

`checks/smoke.py` is a standalone Python 3 script with no dependency beyond the standard library, run by `make smoke` and joined to `make check` after the corpus. It drives `uv` as a subprocess and asserts, in order:

1. **The wheel builds** from `prototype/`, into a throwaway directory outside the repository.
2. **An environment installs it.** The environment is created on the Python version `prototype/.python-version` names, so the supported version is declared once.
3. **The command resolves on that environment's executable directory alone**, and the path it resolves to is outside the repository.
4. **`--version` reports the version and the profile identifier**, run from a directory unrelated to the repository with `PATH` holding the environment's executable directory and nothing else.
5. **A reference bundles from a source root outside the repository**, invoked the same way, producing the expected bundle on standard output, nothing on standard error, and status zero.
6. **The glossary ships with the installed build**, at `prosiform/docs/glossary.md` in the environment's site packages.

The discriminating property the validation scope asks for falls out of steps 3 to 5: the invoked environment inherits no variable from the caller, its `PATH` holds one directory, its working directory is a temporary one, and the source root it bundles from is a tree the script writes beside it. An entry point resolvable only from a checkout fails step 3, because no console script exists to find; one that reads the repository fails step 5, because the repository is on neither the path nor the search.

### What the smoke run does not observe

- **Installation on another platform.** The run observes this host and the continuous-integration runner. Windows path and script-wrapper behaviour is unobserved.
- **An absent checkout.** The repository exists on disk during the run; it is merely unreachable by path, working directory and environment. A build installed on a machine that never held the repository is the adversarial case, and it is declared `awaiting = "I00:E10"`.
- **The documented `pip install ./prototype` route.** The run installs a built wheel, which is what an environment receives either way, but the README's own command line is not the one executed. Declared `awaiting = "I00:E10"`.

### Documentation

`make smoke` is a declared target, so `make tables` requires a `Command` row for it in a README on the same change. It takes one in the repository's check table and one in `checks/README.md`, and the Installation section states the three properties an entry point satisfies and names the run that proves them.

## Acceptance Criteria

- [ ] **AC1.** An installed entry point bundles a reference from a source root without the caller knowing the repository's location, as the installation smoke run shows.

## Test Requirements

| Test | Command | Observes | Asserts |
| --- | --- | --- | --- |
| T1 | `make smoke` | AC1 | The wheel builds, an environment installs it, the command resolves on that environment's executable directory alone and outside the repository, and from an unrelated working directory with that directory as the whole path it reports the profile identifier and bundles a reference from a source root outside the repository. |
| T2 | `make tables` | AC1 | `make smoke` is a declared target named by a command table, so the entry point's proving run is documented where the other checks are. |
| T3 | `make check` | AC1 | The whole gate, the smoke run among it, so installation is held on every change rather than at release time. |

A run proving the smoke check discriminates accompanies T1: the console entry point is removed from `prototype/pyproject.toml`, `make smoke` is run, and the observed failure is recorded before the declaration is restored.

## Overview

The link check reports a reference that does not resolve and a host that did not answer as two verdicts, and only the first fails the run.

## Problem

One request decides each reference, and every outcome it produces reads as a defect in the repository.

- **A server error is the host's trouble, not the document's.**
  A host answering 503 has said nothing about whether the target is there, and the check records it the way it records a path that does not exist.

- **A single attempt cannot tell a blip from an outage.**
  A host restarting behind a load balancer answers the next request, and nothing asks it twice.

- **A failing verdict with no remedy trains the reader.**
  The run is red, the document is right, and the only move is to run it again. A reader who learns to re-run a check stops reading its output, which is how a genuine broken reference gets through.

## Proposal

What the host said decides the verdict. A status of 400 or above below 500 is an answer about the target and holds the document to it. A status of 500 or above, a connection that failed and a request that timed out are the host saying nothing.

An address the host said nothing about is attempted three times with a delay that grows between attempts, and an outcome the host did state is returned on the attempt that produced it. An address still silent after the third attempt is counted as unreachable, reported on a WARN line and counted beside the references that resolved. The run passes.

An offline run is not this case. Without the online flag a remote reference still counts as unresolved, because the reader chose not to look rather than the host choosing not to answer.

The same separation applies to a tracker reference read through the GitHub API: a call that timed out, or came back carrying a server status, is the host saying nothing. A missing command is the caller's to fix and fails the check.

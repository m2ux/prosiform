## Overview

The eval has one form for compiled material: a `compiled` session receives the finished bundles with the build under test as `pf` and a shell limited to `pf`, so it can run bare `pf` for the guide and compile `↳` lines. `staged` folds into it.

## Problem

- **A compiled session cannot run `pf`.**
  The `compiled` form gives a session the bundle set without the build, and a Claude session in it carries no shell, so a bundle whose first line says to run bare `pf` asks for what the form withholds, and the dispatch rules are in a guide the session cannot read.
- **Two forms differ only by the build.**
  `staged` is the compiled bundle set with the build on the session's path, and E04 AC26 gives a staged Claude session a shell. Once `compiled` carries the build, the two are one form.
- **The README describes the retired section.**
  The `compiled` form's row states the Prosiform section `pf` emits around each bundle.

## Proposal

**The scene.** `harness.py` builds each harness's session per form and `run.py` names the forms; `staged` alone carries the build on its path and, for Claude, `Bash(pf:*)`.

- **One compiled form.** (User, 2026-11-03.)
  A `compiled` session receives the finished bundles, the build under test as `pf` on its path, and a shell limited to `pf`; on Claude, the allowlist E04 W18 gave `staged`, `Bash(pf:*)`. This restates E04 AC26 for `compiled`, which supersedes it. `authored` is unchanged.
- **`staged` retires.**
  `run.py` and the harnesses name no `staged` form, and a run naming it is refused as an unknown form. E04 W19 moves the scenarios written only in `staged` to `compiled`.
- **The README follows.**
  The forms table states one `compiled` form, the run-pf line, the dispatch sections and the guide.

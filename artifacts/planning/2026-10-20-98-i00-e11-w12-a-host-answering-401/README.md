## Executive Summary

This record holds the local plan for the row that decides how the link check reads a host answering 401, and one answering 405, to both methods. Whichever reading the evidence supports is stated in the check's README beside the verdict boundary and held by tests against the loopback server, including the case where the boundary stays where it is.

It matters because a live home page refusing this check with an authorization status reddens a branch over a reference a reader can follow, which is the defect the unreachable verdict exists to prevent. The reasoning that moved 403 does not transfer unexamined: an authentication status can name a scheme the caller could satisfy, so the evidence decides rather than the analogy.

The answer is that both are held to and the boundary stays at 500 or above with 403 beside it. 405 does not move with the caller, so a host refusing both methods serves the reader what it served the check; 401 does move with the caller, and is held to because it is also the status `gh api` returns when the check's own credentials are missing. The measurement behind each is recorded in [validation.md](validation.md).

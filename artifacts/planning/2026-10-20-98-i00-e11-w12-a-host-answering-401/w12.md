**Component:** [`checks/links.py`](https://github.com/m2ux/prosiform/blob/main/checks/links.py)

## Overview

The verdict a host answering 401, and one answering 405 to both methods, takes: decided on evidence, stated beside the boundary, and held by tests.

## Problem

The link check tells a reference that does not resolve from a host that said nothing, and the boundary sits at 500 or above with 403 beside it. 401 and 405 fall on the failing side by falling through rather than by a decision, and [#98](https://github.com/m2ux/prosiform/issues/98) names one live home page answering 401 to both methods.

- **The 403 reasoning does not transfer unexamined.**
  403 moved because the refusal turns on the requesting network rather than on the target. Whether 401 and 405 do the same is a measurement, not an analogy.

- **Neither reading is free.**
  Counting a status as silence publishes a reference nobody can follow as resolved. Holding the document to it reddens a run for a reference a reader can follow.

- **The record says the 405 evidence is absent.**
  W11 found no host refusing `GET` on a live address, so the status kept the failing verdict with no measurement behind it.

## Proposal

The boundary stays where it is. 401 and 405 are each an answer about the target and the document is held to both, stated in `checks/README.md` beside the 403 paragraph and in the module's own `verdict`, so a reader meets the reason rather than the fall-through.

The two readings rest on different evidence, and the record carries the measurement for each.

- **405 is a fact about the target.**
  The status names the methods the address allows. The method the check falls back to after a refused `HEAD` is `GET`, which is the method a reader's browser uses, so a host refusing both is serving no reader. The refusal does not move with the caller: it holds for a browser's user agent as readily as for the check's.

- **401 turns on the caller, and is held to anyway.**
  The status names an authorization scheme, so a reference a reader must hold credentials to follow is one the document should say so about. One live host uses it as a bot defence, which is the cost. Against that cost sits a larger one: `gh api` answers 401 when this check's own credentials are missing or stale, so counting 401 as silence would let a run that verified no tracker reference at all warn and pass. 401 is the one status that can name the check's own standing.

- **The `HEAD` then `GET` re-ask is the method question, not the credentials question.**
  403 and 405 on `HEAD` are re-asked with `GET`, because either may be about the method. 401 is decided on the answer to `HEAD`, because credentials do not vary with the method.

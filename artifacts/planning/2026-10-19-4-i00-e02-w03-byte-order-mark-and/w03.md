## Overview

The transport metadata a source carries ahead of its content — one optional leading byte-order mark and one leading frontmatter block — is removed before the parse, the removal is recorded so a diagnostic still names the line of the original file, and a source that is not valid UTF-8 fails as the source defect it is.

## Problem

Three things are wrong with what a run currently does to the bytes it reads.

**Transport metadata reaches the parse.** A byte-order mark is a text-file convention, and a frontmatter block is metadata for whatever reads the file; neither is instruction content. The command reads a source whole and hands all of it to the parser, so a mark becomes a stray character at the head of the first paragraph and a `---`-delimited block becomes a Setext heading or a thematic break followed by prose the author never meant to publish.

**A source that is not valid UTF-8 returns 4.** `Path.read_text(encoding="utf-8")` raises `UnicodeDecodeError`, which reaches the command's generic handler and is reported as an unexpected internal error. That is the exact inversion the contract forbids in the same breath it declares the status: *do not misreport an internal error as a source-document defect* has a converse, and a source defect reported as an internal condition tells the calling agent the tool is broken when the document is.

**The same read translates line endings.** `read_text` opens the file in text mode with universal newlines, so a CRLF source arrives at the parse as LF. The preservation invariant turns on bytes, the frontmatter rules name the CRLF terminator explicitly, and the corpus runner compares standard output byte for byte — a read that silently rewrites every line ending makes all three measure something other than the file.

And one thing is wrong with what removal would do if it were added naively. Removing a frontmatter block moves every line after it. A diagnostic reporting line 3 of the text the parser read would name line 3 of a file whose line 3 is the closing delimiter. Every location the tool reports for a document carrying frontmatter would be wrong, by the height of the block, in the direction that makes it look plausible.

## Proposal

A source is read as bytes and decoded as UTF-8 with no error handler, its transport metadata is removed by a deterministic scan, and what the parse receives is a value that knows where its first line sat in the file it came from.

### The Scan

`prosiform.source` holds the whole of it. It parses no YAML, reads no metadata and executes nothing: it compares two lines against two literals.

1. One leading byte-order mark is removed, if one is there. Exactly one: a second is content.
2. The text is divided into physical lines. A line ends at a line feed, which a carriage return may precede, and at nothing else — none of the further characters Unicode calls a line break ends a line in CommonMark, and `str.splitlines` would end one at each of them.
3. If the first physical line, its terminator excluded, is the three characters `---`, that line is the frontmatter opener. Anything else, and the document has no frontmatter.
4. The block closes at the next physical line, its terminator excluded, equal to `---` or `...`. The opener, the metadata, the closer and the closer's terminator are removed together, and the body after it — its leading blank lines included — is untouched.
5. A recognized opener with no closer fails with `E_UNTERMINATED_FRONTMATTER`.

The narrowness is the substance. Each of the following is **not** frontmatter, and each falls out of the two comparisons above rather than being excluded by a rule of its own:

| Written | Why it is not an opener |
| --- | --- |
| ` ---` | The line is not the three characters; a leading space is a character. |
| `--- ` | The same, for a trailing one. |
| `+++`, `{` | Neither is `---`. TOML and JSON metadata are not v1 frontmatter. |
| A blank line, then `---` | The first physical line is the blank one, so the `---` under it is body: a thematic break the author wrote. |
| `---` inside a code block | The first physical line opens the fence, not the block. |
| `---` after content | It is not the first physical line. |

A document meaning to open on a horizontal rule spells it another way, `***` among them. The leading `---` is reserved, and that is the cost of recognizing frontmatter at all.

### How the Coordinate Shift Is Recorded

The read returns a `Source`: the content after the removal, and `first_line`, the one-based line of the original file that content's first line occupies.

```python
@dataclass(frozen=True)
class Source:
    text: str
    first_line: int = 1
```

The invariant is one line of arithmetic, stated once and applied wherever a parsed location becomes a reported one: **a location at line `n` of `text` is at line `n + first_line - 1` of the file.** `Source.line()` is that expression, and the command's `location()` takes its result. With no frontmatter removed `first_line` is 1 and the mapping is the identity, so the untouched case needs no separate path.

A byte-order mark occupies no line of its own — it sits at the head of line 1, which remains line 1 — so it shifts no coordinate and contributes nothing to `first_line`. Only the block does.

Three alternatives were considered and rejected.

- **Replace the block with blank lines.** The coordinates would need no record at all, but the parse would then read content the file does not carry, and a blank line before a Setext underline or at the head of a list changes what the document means. A removal that changes the parse is not a removal.
- **Record a byte offset.** Diagnostics report lines, so an offset would have to be converted back at each use, over text the converter no longer holds.
- **Carry the original text alongside the stripped text.** Two strings in hand is two chances to parse the wrong one. One string and one integer cannot be confused.

The record is a line count rather than a full map because this task removes exactly one contiguous leading region. The first later transformation that removes or inserts a region in the middle of a document will need a map, and `Source` is where that map replaces the integer.

### What the Encoding Failure Carries

A source must be valid UTF-8, and one that is not fails. The decode is `bytes.decode("utf-8")` with no `errors` argument, so the strict handler raises rather than substituting `U+FFFD`: a replacement character is a byte the tool invented, published as though the author had written it, under a promise that selected content is preserved.

**No code in the catalogue names this failure.** The design's error codes are the twelve the schema enumerates, and the nearest two are about where a path resolves, not about what the bytes at that path are. The failure therefore carries a severity, a message naming the offending byte and the reason the decoder gave, a remedy, and **no code**, which is what the contract requires of a defect it has not declared. None is invented here. W07 is the row that closes this gap and already lists eight uncoded outcomes; this is a ninth, and it is reported to that row rather than patched here.

The consequence is exact and worth stating, because it decides what AC8's evidence can be. A fixture manifest requires a catalogued code for every diagnostic it declares, so the corpus structurally cannot express a run whose only diagnostic has no code. **AC8's failing direction is held by unit tests until W07 lands a code for it**, and the encoding fixture the criterion names is written on the change that adds that code. The same reasoning held for three of W02's refusals, and the same boundary applies: a statement the corpus cannot make belongs in the build's own suite, stated there rather than left unstated.

### Where It Plugs In

`read_entry` already runs suffix check → root containment → existence → parse. The removal and the decode sit between existence and parse, in that order, because nothing can be scanned before it is text:

1. Read the bytes. `Path.read_bytes`, so no newline translation happens and a CRLF source reaches the scan as the file wrote it.
2. Decode as UTF-8, strictly. A failure here is an input failure with no code.
3. Remove the transport metadata. An unterminated opener is an input failure with `E_UNTERMINATED_FRONTMATTER`, reported at line 1, which is where the opener the run could not close sits.
4. Parse the `Source`'s text, and map every location the parse reports back through `first_line`.

The order matters in one more way: the scan runs over decoded text rather than over bytes, so a byte-order mark is the character `U+FEFF` rather than three bytes whose meaning depends on an encoding not yet established.

### The Placeholder Still Stands

A run whose sources read, strip and parse cleanly still returns **4**. Reading a source is not bundling it, W04 delivers the stage that is missing, and W01's placeholder says so honestly rather than returning 0 having published nothing. This row makes more sources fail earlier and correctly; it makes no source succeed.

### The Fixtures This Row Adds

The design's `## Adversarial acceptance fixtures` names the family case by case — *optional BOM, exact opening/closing delimiters, `...` termination, leading-blank-line distinction, malformed delimiters, and missing closers* — and `fixtures/frontmatter/` gains one fixture for each.

| Fixture | Declares |
| --- | --- |
| `optional-mark` | A byte-order mark and a `---`-closed block both absent from the bundle, the body after them unchanged |
| `dot-terminated` | A block closed by `...` |
| `crlf-delimiters` | An opener and closer terminated by CRLF recognized, and the closer's CRLF removed with it |
| `unterminated-block` | An opener with no closer failing with `E_UNTERMINATED_FRONTMATTER` at line 1 |
| `leading-blank-line` | A blank line before the `---`, which makes that `---` a thematic break the bundle carries |
| `indented-delimiter` | A one-space indent, which is not the delimiter |
| `delimiter-with-trailing-spaces` | A trailing space, which is not the delimiter either |
| `toml-fence` | `+++`, which is not v1 frontmatter |
| `yaml-example-in-a-code-block` | A YAML block inside a fence and a thematic break below the first line, both content |

Eight declare the bundle the contract names and so expect status 0; each fails today on the absent bundling stage, exactly as the seven fixtures already in the corpus do, and each passes when W04 lands. `unterminated-block` declares a failure this build produces in full, so it passes on this row.

A removal rule observed only removing is half tested, which is why six of the nine are cases where nothing is removed.

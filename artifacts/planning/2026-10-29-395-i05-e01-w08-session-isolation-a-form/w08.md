**Component:** evals/diagram-following/run.py

## Overview

A session is given one form of one workflow and the instruction, and nothing else. This task holds that boundary: the agent's environment carries no context from the caller's machine, so a pass measures the agent reading the form rather than the agent obeying a second instruction set that arrived alongside it.

## Problem

- **A plugin hook injects another repository's rules into every session.**
  All 200 sessions of run `20261029T143428Z` received a `SessionStart` hook whose `additionalContext` carries 670 characters: `For work in shieldedtech or midnightntwrk repositories, apply the shielded-core-rules skill ... Changes to shared or external state require explicit user approval`. It arrives as a `hook_response` immediately after `SessionStart:startup`, so it reaches the model before the first API call in every session.
- **The hook comes from the eval's own config directory.**
  `~/projects/eval/prosiform/config/plugins/installed_plugins.json` holds `shielded-core-rules@shieldedtech` at `scope: managed`, and its `hooks/hooks.json` declares the `SessionStart` command. The isolation the eval relies on is breached by the directory the eval created to provide it.
- **The flags in use do not suppress it.**
  `--disable-slash-commands` disables skills and `--strict-mcp-config` disables MCP servers, but neither touches a plugin's hooks. `--bare` skips hooks from settings and installed plugins, and is unusable here because it stops reading the OAuth login the eval depends on, holding auth to `ANTHROPIC_API_KEY` or an `apiKeyHelper`.
- **Telemetry leaves the session.**
  The same directory's `remote-settings.json` sets `CLAUDE_CODE_ENABLE_TELEMETRY` and an OTLP endpoint, so a session reports to a collector outside the run. `environment()` scrubs `CLAUDE*` and `ANTHROPIC_*` from the caller, and the agent sets them again from these remote settings.
- **Nothing observes the boundary.**
  The runner's tests assert the tools, `--strict-mcp-config`, `--disable-slash-commands` and the absence of `CLAUDE*` in the inherited environment, which is the caller's side of it. No test reads what the agent injected into the session, so the regression is invisible to `make check`.

## Proposal

- **The config directory carries no plugin and no remote settings.**
  `preflight` refuses a run whose config holds an installed plugin or a remote-settings file that enables one, naming the path to remove, so a session cannot start with a hook the eval did not write.
- **The injected context is observed, not assumed.**
  A session's `transcript.jsonl` is read for any context the agent added before its first turn — a `hook_response`, an appended system prompt, a memory file — and a run fails on one that is not the run's own instruction, naming what it carried.
- **Isolation is a property the tests hold.**
  The stub reports the context it received, and a test plants a plugin hook in a temporary config directory to show the preflight refuses it and that a clean directory starts the session.
- **The documentation states the boundary it holds.**
  The README's isolation paragraph names what is suppressed and by which mechanism, and what the preflight checks, in place of a list of what the caller is kept from.

## Acceptance Criteria

- [ ] **AC1.** A run whose config directory holds an installed plugin hook is refused before its first session starts, naming the path that holds it, as a stub-agent test `make check` runs shows.
- [ ] **AC2.** A session whose agent injected context the run did not supply fails the run, naming what it carried, as a stub-agent test `make check` runs shows.
- [ ] **AC3.** The eval's README states each mechanism that keeps a session to its form, and what the preflight refuses, as an inspection of the documentation shows.

## Open Questions

- **Whether the login can move out of the config directory.**
  The plugin and remote settings arrive under `CLAUDE_CONFIG_DIR` because that is also where the OAuth login lives. Isolating them without isolating the login would need the login supplied another way, such as `apiKeyHelper` through `--settings`, which `--bare` then permits. Whether that is worth the change, or the preflight refusal is sufficient, is undecided.

## Findings

- **Every session of the run carried the hook.**
  `20261029T143428Z` recorded a `SessionStart:startup` hook and its 670-character response in all 200 transcripts, at zero cost, because the hook runs before the API call the login refused.
- **A refused run is recorded as a completed one.**
  The same run records 200 started, `cost_usd` 0.0 and an empty `not_started`, and wrote a report comparing pass rates. Its sessions are `errored` with `api_error: usage_limit_reached`, so the class works; the run's own record does not show the run was refused.
